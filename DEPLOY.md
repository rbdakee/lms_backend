# Деплой, бэкапы, мониторинг

Локальный запуск — `README.md`. Здесь то, что отличает бой от разработки.

## Три деплоя

```
domain.kz         →  apps/web     (Vercel)
admin.domain.kz   →  apps/admin   (Vercel)
api.domain.kz     →  этот сервис  (свой сервер: docker compose)
```

Сервер бывает двух видов, и от этого зависит, кто держит 443:

- **выделенный** — 80 и 443 свободны, прокси поднимает сам compose
  (профиль `edge`, сертификаты Caddy выпускает сам);
- **общий** — прокси уже стоит на хосте и обслуживает другие проекты.
  Тогда наш Caddy не поднимается вовсе, а сервис слушает `127.0.0.1`
  и в него ходит хостовый прокси.

Разница — один флаг в команде запуска и один блок в чужом конфиге.

Бэкенду нужен долгоживущий сервер: серверные сессии, раздача файлов
по подписанным ссылкам, счётчики лимитов. Файлы лежат в объектном хранилище
PS Cloud (бакет `lms-main`) — площадка в РК, что и требовалось к данным
граждан (`../BACKEND_NOTES.md`, 14).

## Первый выкат

Шаги руками, по порядку. Автоматизации нет нарочно: выкат случается редко,
а каждый шаг ниже виден в ответе команды.

1. **DNS.** `api.domain.kz` A-записью на этот сервер. Сертификат Caddy
   выпустит сам, но только когда домен уже указывает сюда.
2. **Порты.** Наружу открыты 80 и 443 (443 ещё и по UDP — HTTP/3).
   Больше ничего: ни 8000, ни 5432.
3. **Код и окружение.**
   ```sh
   git clone <репозиторий> lms_backend && cd lms_backend
   cp .env.prod.example .env
   # заполнить: домены, пароль базы, ключи S3, секреты, номер админа
   ```
4. **Запуск.** На общем сервере (прокси на хосте):
   ```sh
   docker compose -f docker-compose.prod.yml up -d --build
   ```
   На выделенном — вместе со своим прокси:
   ```sh
   docker compose -f docker-compose.prod.yml --profile edge up -d --build
   ```
   Миграции идут отдельным шагом до сервиса: упавшая миграция останавливает
   выкат, а не поднимает сервис на половине схемы.
5. **Проверка.** `curl https://api.domain.kz/health` → `{"status":"ok"}`.
   Сертификат не выпустился — смотреть `docker compose -f
   docker-compose.prod.yml logs caddy`, там обычно DNS или закрытый 80.
6. **Telegram-вебхук** — один раз, см. ниже.
7. **Вход админа** — по номеру из `AUTH_BOOTSTRAP_PHONE`: код придёт
   в WhatsApp. Не пришёл — разбираться до раздачи адреса людям, см. ниже.
8. **Бэкапы** — по расписанию, см. ниже. Правило владельца: до первого
   живого пользователя.

Обновление потом — тем же `up -d --build`: миграции проходят снова,
сервис пересобирается, база и сертификаты остаются в томах.

## Переменные окружения

Образец боя — `.env.prod.example`, образец разработки — `.env.example`.
Секреты — только в окружении, в репозиторий не уходит ни один `.env`.
В логи они не попадают: проверено на упавшем подключении к базе —
трассировка называет хост и порт, пароля в ней нет.

| Переменная | В бою | Почему |
|---|---|---|
| `ENV` | `prod` | |
| `DATABASE_URL` | своя строка, хост `db` | пароль в окружении, не в репозитории |
| `CORS_ORIGINS` | `["https://domain.kz","https://admin.domain.kz"]` | два фронта, два источника |
| `ADMIN_ORIGINS` | `["https://admin.domain.kz"]` | какая из сторон админка: у неё своя кука сессии. Забыть — вернуть общую куку; сервис поднимется, но напишет предупреждение в лог |
| `COOKIE_DOMAIN` | `.domain.kz` | общий домен; имена кук у приложений разные — `sid` и `sid_admin` |
| `COOKIE_SECURE` | `true` | |
| `TRUST_REAL_IP` | `true` | адрес клиента из `X-Real-IP` — см. ниже |
| `API_PORT` | свободный порт | сервис слушает его на `127.0.0.1`, в него ходит прокси |
| `PUBLIC_BASE_URL` | `https://api.domain.kz` | адрес, с которого фронт качает файл |
| `VERIFY_BASE_URL` | `https://domain.kz` | **не** адрес API: страница `/verify` живёт в клиентском приложении. Пусто — QR на сертификате не печатается |
| `ADMIN_BASE_URL` | `https://admin.domain.kz` | кнопка «Открыть в админке» в уведомлениях бота — третий деплой, не API |
| `STORAGE_PROVIDER` | `s3` | локальный каталог — только разработка |
| `S3_ENDPOINT_URL` | `https://object.pscloud.io` | адрес площадки, а не бакета |
| `S3_BUCKET` | `lms-main` | приватный |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | из панели PS Cloud | |
| `STORAGE_SECRET` | длинная случайная строка | подпись ссылок на файлы |
| `TELEGRAM_PROVIDER` | `bot` | вместе с токеном, именем бота и секретом вебхука |
| `SMS_PROVIDER` | `whatsapp` | код входа уходит шаблоном WhatsApp — см. ниже |
| `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN` | из Meta Business Manager | пустые роняют сервис при старте |
| `WHATSAPP_TEMPLATE_NAME`, `_LANGUAGE`, `_HAS_BUTTON` | `otp_ru`, `ru`, `true` | как шаблон заведён в Meta |
| `AUTH_BOOTSTRAP_PHONE` | номер первого админа | на чистой базе иначе некому выдать доступ |
| `AUTH_BOOTSTRAP_CODE` | **пусто** | бэкдор на случай, когда код не доходит — см. ниже |

Опечатка в `SMS_PROVIDER`, `TELEGRAM_PROVIDER` или `STORAGE_PROVIDER` роняет
сервис при старте, а не на первой заявке учителя (`app/config.py`,
`check_providers`). Там же проверено, что у `s3` есть адрес и ключи,
у `whatsapp` — номер отправителя и токен, а у фиксированного кода — номер,
к которому он относится.

### Код входа приходит в WhatsApp

`SMS_PROVIDER=whatsapp` — код уходит **согласованным шаблоном** категории
Authentication через Cloud API (`app/adapters/sms/whatsapp.py`). Шаблон, а не
обычный текст: свободное сообщение WhatsApp принимает только внутри
24-часового окна — то есть если человек сам написал на этот номер за
последние сутки. На входе это никогда не так, и Meta отвечает `131047`.

Что нужно на стороне Meta, и это делается один раз руками:

1. **WABA и номер отправителя.** `WHATSAPP_PHONE_NUMBER_ID` — идентификатор
   номера, а не сам номер.
2. **Постоянный токен системного пользователя.** Токен из «Get started»
   живёт сутки и в бою не годится.
3. **Согласованный шаблон** категории Authentication с одним параметром —
   кодом. Имя и язык в `WHATSAPP_TEMPLATE_NAME` и `_LANGUAGE`.

Отдельно про кнопку. Шаблон Authentication у Meta по умолчанию идёт
с кнопкой «Скопировать код», и тогда API требует код **дважды** — в теле
и в кнопке. Это `WHATSAPP_TEMPLATE_HAS_BUTTON=true`. У шаблона без кнопки
лишний параметр вызовет отказ, и значение нужно поменять на `false`.

**Ограничение, которого не было у SMS:** учитель без WhatsApp на своём
номере войти не сможет вовсе — второго канала нет. Экраны входа об этом
говорят прямо («отправим код в WhatsApp»), и в FAQ на главной это тоже
написано.

Заглушка `log` осталась версией для разработки: печатает код в лог сервиса
и никуда не ходит. В бою она означала бы, что войти может только тот,
кто читает логи.

### Первый админ

Прод поднимается с пустой базой: пользователей нет, а значит нет и того, кто
выдаст первый доступ и заведёт курс. Это закрывает одна переменная:

```
AUTH_BOOTSTRAP_PHONE=+7XXXXXXXXXX
```

Номер заводится админом при старте (`app/application/bootstrap.py`,
идемпотентно) и входит обычным кодом — тем, что придёт ему в WhatsApp.
Снимать переменную после первого входа не нужно и не вредно: `is_admin`
у пользователя остаётся.

### Бэкдор: вход мимо провайдера

Вторая, **необязательная** половина:

```
AUTH_BOOTSTRAP_CODE=XXXX
```

С ней тот же номер входит **фиксированным кодом** вместо случайного
(`app/application/auth.py`, `_code_for`), минуя WhatsApp. Нужна она ровно
там, где кода взять неоткуда: `SMS_PROVIDER=log`, снятый с публикации
шаблон, протухший токен — то есть когда иначе в собственную площадку
не войти.

**Это бэкдор, и называть его надо так.** Что его ограничивает:

- код живёт те же 5 минут и гасится входом;
- три неверных ввода блокируют номер на 10 минут, суточные потолки
  на номер и на адрес считаются как у всех;
- код проверяется при старте: не та длина или код без номера роняют
  сервис, а не молча не пускают.

Чего он не отменяет: знающий номер и код входит админом. Поэтому боевой
номер в репозитории не лежит (в тестах — вымышленный), а сам код в обычном
бою держать включённым не нужно — **в `.env.prod.example` он закомментирован
нарочно**. Снимается снятием переменной, без релиза.

Когда нужда отпадёт совсем — `app/application/bootstrap.py` в части кода
и `tests/test_bootstrap_login.py` удаляются целиком; заведение первого
админа при этом остаётся.

## Telegram-вебхук — один раз после деплоя

Переменные окружения (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`,
`TELEGRAM_WEBHOOK_SECRET`) говорят сервису, чем отвечать. Отдельным шагом
нужно сказать Telegram, **куда** слать апдейты — сервис сам этого не делает,
никакого кода на старте под это нет.

Локально это упирается в туннель: `localhost:8000` снаружи не виден. Поэтому
для разработки есть второй режим — `TELEGRAM_UPDATES=poll` (умолчание —
`webhook`): сервис сам вытягивает апдейты через `getUpdates` фоновой задачей
в своём же процессе (`app/adapters/telegram/poller.py`), вебхук вообще
не участвует, и `setWebhook` вызывать не нужно.

**Одновременно оба не работают** — Telegram отвечает `409 Conflict` на
`getUpdates`, пока для бота зарегистрирован вебхук. Поэтому `TELEGRAM_UPDATES`
в бою — всегда `webhook`: `poll` там не только не нужен (`api.domain.kz`
и так публичный), а ещё и ломает вебхук, если его случайно не убрали.

На `api.domain.kz` туннель не нужен вовсе — домен и так публичный, поэтому
регистрация вебхука — ровно один вызов после первого деплоя (и заново —
если сменили токен бота или домен):

```sh
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
  -d "url=https://api.domain.kz/telegram/webhook" \
  -d "secret_token=$TELEGRAM_WEBHOOK_SECRET"
```

Проверить, что зарегистрировалось:

```sh
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getWebhookInfo"
```

Вызов идемпотентен — повторный `setWebhook` с тем же адресом ничего не ломает,
поэтому автоматизировать его в каждый деплой незачем: делается руками один раз,
как и остальные ручные шаги этого документа.

## Caddy

Прокси перед сервисом. Сертификаты он выпускает и продлевает сам,
отдельного шага в деплое под это нет.

Три вещи, без которых сервис работает неправильно, — и они одинаковы,
свой у нас прокси или чужой.

1. **Адрес клиента** — `header_up X-Real-IP {remote_host}`. Без префикса
   `header_up` **заменяет** присланное клиентом, а не дописывает к нему.
2. **Размер тела** — `request_body max_size` не меньше `UPLOAD_MAX_MB`
   (20 МБ), иначе сдача работы упрётся в прокси, а не в понятный отказ
   сервиса.
3. **Порт сервиса виден только с самой машины.** В `docker-compose.prod.yml`
   он опубликован как `127.0.0.1:${API_PORT}`: до сервиса не должно быть
   дороги мимо прокси, иначе `X-Real-IP` ставит себе кто угодно.

### Свой прокси — выделенный сервер

Конфигурация — `Caddyfile` рядом, поднимается профилем `edge`. Домен берётся
из `API_DOMAIN`, почта для Let's Encrypt — из `ACME_EMAIL`.

### Чужой прокси — общий сервер

Наш Caddy не поднимается (профиль не активируют), а в конфиг хостового
добавляется блок. Он повторяет ровно те же три вещи:

```
api.lms.example.kz {
	reverse_proxy 127.0.0.1:8010 {
		header_up X-Real-IP {remote_host}
	}

	request_body {
		max_size 20MB
	}
}
```

Дальше `caddy validate --config /etc/caddy/Caddyfile` и
`systemctl reload caddy` — перезапуск не нужен, reload не рвёт чужие
соединения. Сертификат выпишется сам, когда домен уже указывает на машину.

**Раздатчика файлов здесь нет, и он не нужен.** Раньше на этом месте
предполагался nginx с `secure_link_md5`: подпись проверял бы он, а байты
брал бы с диска. С объектным хранилищем диска нет, и байты стримит сам
сервис — он же проверяет свою подпись (`app/application/files.py`,
`content`). Секрет `STORAGE_SECRET` поэтому живёт в одном месте, а не в двух,
и сходиться ему не с кем.

Цена решения известна: файлы идут через сервис, а не мимо него. При 20 МБ
на файл и одном воркере это приемлемо, а видео сегодня и вовсе на YouTube
(`../BACKEND_NOTES.md`, 9). Понадобится отдавать байты мимо сервиса — это
пресайн-ссылки хранилища, отдельная работа и отдельное решение: они ведут
на чужой домен и живут по чужим правилам.

### Адрес клиента — решено 21.08.2026

На адресе держатся два лимита: суточный потолок SMS (30 на адрес)
и публичная проверка сертификата (20 в минуту на адрес).

Вопрос был открыт с 20.08.2026 и звучал так: `TRUST_FORWARDED_FOR=false`
за прокси означает, что все запросы приходят с адреса прокси — потолки
превращаются в «30 SMS в сутки на всю страну». А `true` брал первый элемент
`X-Forwarded-For`, который клиент приписывает себе сам, — ведро выбирал
клиент. Ни одно из двух значений не годилось.

Решение — то, которое в прошлой редакции этого документа было названо
правильным:

- Caddy ставит `X-Real-IP` равным адресу соединения, **заменяя** присланное;
- сервис читает **только** `X-Real-IP` и не читает `X-Forwarded-For` вовсе
  (`app/api/deps.py`, `get_client_ip`);
- поэтому число прокси перед сервисом перестаёт иметь значение, а подделать
  адрес клиенту нечем — до сервиса нет дороги мимо прокси.

Переключатель остался, но сменил имя и смысл: `TRUST_REAL_IP` (в бою `true`,
локально `false` — прокси там нет). Проверено тестами: заголовок делит вёдра
при включённом доверии, не делит при выключенном, а `X-Forwarded-For`
не читается ни в одном из режимов (`tests/test_limits.py`).

Два места, где адрес по-прежнему может отсутствовать, оставлены как есть,
и в бою они недостижимы: `ip or "unknown"` в `app/application/certificates.py`
(все клиенты без адреса делят одно ведро) и `count_in_day(ip=ip) if ip else 0`
в `app/application/auth.py` (без адреса суточный потолок на IP не считается).
Заголовок ставит Caddy каждому запросу — адреса нет только у запроса,
пришедшего мимо него, а такой дороги нет.

## Сколько воркеров uvicorn — решено

`Dockerfile` поднимает **один** процесс: `--workers 1` стоит в команде явно.
При одном процессе три лимита работают ровно как настроены, потому что
их счётчики лежат в памяти процесса (`app/application/ratelimit.py`).

При W воркерах потолок для одного клиента становится W × настроенного:

| Лимит | Настроено | 1 воркер | 4 воркера |
|---|---|---|---|
| `playback_per_min` | 10/мин | 10 | 40 |
| `verify_per_min` | 20/мин | 20 | 80 |
| `thread_messages_per_min` | 3/мин | 3 | 12 |

Суточных потолков SMS это не касается: они считаются в базе и одинаковы
при любом числе процессов.

**Решено 20.08.2026: один воркер.** Закреплено в `Dockerfile` явным
`--workers 1` с объяснением — раньше правильное поведение держалось
на умолчании uvicorn, и `--workers 4` ломал его молча. Менять число —
только вместе с переездом счётчиков в базу.

## Health и балансировщик

`GET /health` ходит в базу (`SELECT 1`) и отвечает:

- `200 {"status": "ok"}` — запросы обслуживаются;
- `503 {"error": {"code": "not_ready", ...}}` — база не отвечает.

Балансировщик вешать на эту ручку, снимать инстанс с трафика по `503`.
До сессии 8 ручка не заглядывала в базу и отвечала `200` тогда, когда всё
остальное отдавало `500`: сломанный инстанс оставался в трафике, а раскатка
считала сломанную версию здоровой. Решено владельцем 20.08.2026.

## Бэкапы

Правило владельца: не «настроены», а **один раз восстановлены на чистую базу
и проверены запуском приложения поверх**. База и файлы снимаются **вместе**:
порознь они бесполезны — ссылка без файла и файл без ссылки одинаково мертвы.

Файлы теперь лежат в бакете, а не на диске сервера, и на процедуру это влияет
меньше, чем кажется: ключ объекта в бакете (`uploads/2026/08/21/...`) — это
ровно тот путь, по которому тот же файл лежал бы у локального адаптера.
Поэтому снятая копия бакета кладётся в обычный каталог, а приложение поверх
неё поднимается с `STORAGE_PROVIDER=local` — второй бакет ради проверки
заводить не нужно.

### Снять

```sh
pg_dump -U lms -d lms --format=custom --file=lms.dump
s3cmd sync s3://lms-main/ storage-backup/
```

`s3cmd` настраивается на `object.pscloud.io` теми же ключами, что и сервис;
годится и любой другой синхронизатор (`aws s3 sync`, `rclone`) — важно, что
раскладка каталогов совпадает с ключами.

### Восстановить и проверить

Восстановление проверяется **на чистой базе**, а не поверх рабочей.

```sh
# 1. Чистая база — отдельная, ни боевую, ни тестовую не трогаем
psql -U lms -d postgres -c "CREATE DATABASE lms_restore_check OWNER lms;"
```

Что сверить — по порядку, каждый пункт своим числом:

1. `pg_restore --exit-on-error` прошёл без ошибок.
2. Число строк совпадает по **каждой** таблице, а не в сумме.
3. Число индексов совпадает.
4. `alembic_version` тот же, что был.
5. Последовательности продолжают ряд: первая созданная запись получает

7. Контрольные суммы файлов совпадают побайтово, и число объектов в копии
   совпадает с числом в бакете.
8. База и файлы восстановлены **совместно**: `GET /branding/logo` отдаёт те же
   байты, что лежат в бакете.

## Мониторинг и разбор ошибок

Что есть сегодня:

- Логи — в stdout, забирает docker (`docker compose -f docker-compose.prod.yml
  logs -f api`). Уровень `INFO`.
- Один формат ошибки на все ручки (`app/api/errors.py`). Наружу уходит код
  и человеческое сообщение; текст исключения — никогда, в нём бывают данные
  запроса.
- Необработанная ошибка пишет в лог метод и путь, без тела и без параметров
  запроса.

За чем смотреть:

- `internal_error` в логе — это всегда дефект, их должно быть ноль.
- **Отказы хранилища.** `AccessDenied` и `NoSuchBucket` наружу уходят как
  `internal_error`, а в логе видны как `ClientError`: это всегда ключи
  или имя бакета, а не сбой. «Объекта нет» к ним не относится — это
  контрактное 404 (`app/adapters/storage/s3_storage.py`, `size`).
- «Telegram-уведомление о заявке N не ушло» — заявка в админке есть,
  а админ о ней не знает. После сессии 8 отправка идёт тремя попытками
  с паузами, но времени это говорит мало: отказ сети (нет маршрута,
  NXDOMAIN, connection refused) возвращается мгновенно, и три попытки
  укладываются в секунду. Долгие 16 секунд — только когда Telegram
  принимает соединение и молчит.
- Отказы `rate_limited` на `/auth/request_code` — либо чей-то перебор,
  либо `TRUST_REAL_IP` выключен и потолок на адрес схлопнулся в общий.
- **Отказы `send_failed` на `/auth/request_code`** — код не ушёл, и человек
  на входе это видит. В логе рядом лежит код ошибки Meta, и он говорит,
  что чинить: `131047` — отправлен свободный текст вместо шаблона,
  `132001` — шаблона с таким именем или языком нет, `190` — протух токен,
  `131030` — номер получателя не в списке разрешённых (бывает только
  у тестового номера Meta). Ноль таких отказов — норма.
- Предупреждение `AUTH_BOOTSTRAP_CODE` в логе при старте — напоминание,
  что вход мимо провайдера всё ещё включён.

### Персональные данные

ФИО, телефоны, школы и регионы учителей не попадают в логи, в трассировки,
в текст ошибок и в метрики. Как это держится сегодня:

- и заглушка, и адаптер WhatsApp печатают номер как `***0011` — четыре
  последние цифры; код входа и токен в лог не попадают вовсе;
- уведомления админу в Telegram несут номер заявки и название курса,
  но **не ФИО и не телефон**: «подробности админ откроет в админке»;
- вебхук Telegram не пишет в лог ни тела запроса, ни текста сообщения —
  там переписка людей;
- предупреждение о входе без SMS называет переменную, но не номер;
- ответ `500` наружу — всегда общий `internal_error` без подробностей.

Заводя любой новый вывод в лог, проверять по этому списку. Отдельный сборщик
ошибок (Sentry и подобные) не заведён: это новая зависимость и новый адрес,
куда уезжают трассировки, — решение владельца.
