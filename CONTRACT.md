# Контракт API

Фронт работает от примеров из этого файла и не гадает. Форма ответа меняется
только вместе с этим файлом.

## Общие правила

- Всё, что пересекает границу, — через `_`: поля JSON и пути
  (`/quiz_attempts`, не `/quiz-attempts`).
- Время — ISO 8601 в UTC: `"2026-08-16T09:30:00Z"` (может прийти и как
  `+00:00`). Показ по казахстанскому времени — забота фронта.
- Сессия — кука HttpOnly, `SameSite=Lax`, **host-only**: домена у неё нет вовсе,
  каждый домен держит свою. Имя зависит от приложения: `sid` у кабинета учителя,
  `sid_admin` у админки — сервер узнаёт её по `Origin` запроса. Два входа поэтому
  живут в одном браузере одновременно. Фронт токен не видит и не хранит, запросы
  шлёт с `credentials: "include"`.
- **Площадку сервер узнаёт по `Origin`** (`PLATFORM_ORIGINS`), тем же способом
  и по той же причине, что и приложение. Ни в одном запросе площадку передавать
  не нужно — единственное исключение названо явно (`POST /admin/enrollments`).
  Неизвестный источник, отсутствие `Origin` и админка — первая площадка.
- Успешный ответ без тела — `204 No Content`.

## Формат ошибки — один на все эндпоинты

```json
{
  "error": {
    "code": "wrong_code",
    "message": "Неверный код",
    "details": { "attempts_left": 2 }
  }
}
```

- `code` — машинное имя для ветвления на фронте, `message` — готовый текст
  по-русски, `details` — данные для экрана; поля нет, если показывать нечего.
- Ошибка валидации (422) всегда несёт список полей:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": {
      "fields": [
        { "field": "phone", "message": "Field required" }
      ]
    }
  }
}
```

- **Текст в `fields[].message` — готовая строка по-русски**, её показывают
  под полем как есть: это касается и проверок сценария («Без названия курс
  не сохранить»), и границ числовых полей («Объём курса — от 1 до 999 часов»).
  По-английски отвечает только разбор самого запроса — поля нет вовсе или
  прислан не тот тип (`"Field required"`): это ошибка клиента, а не человека,
  и до подписи под полем она доходить не должна.
- Лимиты (429) всегда несут `details.retry_after_sec`.
- Коды, общие для всех эндпоинтов: `unauthorized` (401 — нет или умерла
  сессия), `blocked` (403 — учитель заблокирован), `forbidden` (403),
  `not_found` (404), `validation_error` (422), `rate_limited` (429),
  `internal_error` (500).
- `send_failed` (502) — код входа не ушёл: провайдер недоступен или отверг
  сообщение. Отдельно от `internal_error`, потому что человеку это говорит
  разное: здесь помогает вторая попытка, и ждать минуту не нужно —
  не ушедший код строкой в базе не остаётся.

## Постраничные списки

Запрос: `?page=1&per_page=20` (per_page ≤ 100). Ответ:

```json
{ "items": [], "total": 0, "page": 1, "per_page": 20 }
```

Пустая страница — это `items: []` с настоящим `total`, а не ошибка.

## Здоровье

`GET /health` → `200 {"status": "ok"}`

**Изменено в сессии 8:** ручка ходит в базу и при недоступной базе отвечает
`503` с обычным телом ошибки (`code: "not_ready"`). Раньше она отвечала `200`
и тогда, когда все остальные ручки давали `500`, — балансировщик не отличал
сломанный инстанс от живого. Читает её балансировщик, а не фронт.

```json
// 503 not_ready — база не отвечает
{ "error": { "code": "not_ready", "message": "Сервис не готов принимать запросы" } }
```

# Сессия 2 — вход и люди

Экраны: `/login`, `/onboarding`, `/profile`.

## POST /auth/request_code

Просит SMS-код. Согласие обязательно — без галочки кнопка на экране и так
неактивна. Телефон принимается в любом виде (`8 707…`, `+7 (707)…`),
хранится как `+7XXXXXXXXXX`.

```json
// запрос
{ "phone": "+7 (707) 123-45-67", "consent": true }

// 200 — когда можно просить следующий код (таймер на экране)
{ "retry_after_sec": 60 }
```

Ошибки:

```json
// 422 validation_error — номер не казахстанский или нет согласия
{ "error": { "code": "validation_error", "message": "Проверьте номер: нужен казахстанский, 10 цифр после +7" } }

// 429 rate_limited — код уже отправлен или суточный потолок
{ "error": { "code": "rate_limited", "message": "Код уже отправлен — новый можно запросить через минуту", "details": { "retry_after_sec": 41 } } }

// 429 too_many_attempts — ввод для номера заблокирован (после 3 неверных кодов)
{ "error": { "code": "too_many_attempts", "message": "Ввод кода заблокирован на 10 минут", "details": { "retry_after_sec": 583 } } }

// 403 blocked — учитель заблокирован админом
{ "error": { "code": "blocked", "message": "Доступ заблокирован. Напишите нам, если это ошибка." } }

// 502 send_failed — провайдер не принял сообщение или недоступен.
// Повтор разрешён сразу: минуты ожидания здесь нет, строка кода удалена
{ "error": { "code": "send_failed", "message": "Не удалось отправить код — попробуйте ещё раз" } }
```

## POST /auth/verify_code

Проверяет код, ставит куку сессии (`sid` или `sid_admin` — по `Origin`),
возвращает пользователя. Код 4 цифры,
живёт 5 минут, действителен последний отправленный, попытки — 3.

```json
// запрос
{ "phone": "+7 (707) 123-45-67", "code": "4812" }

// 200 — пользователь; onboarding_done решает, куда вести: /my или /onboarding
{
  "id": 1,
  "phone": "+77071234567",
  "first_name": "",
  "last_name": "",
  "middle_name": "",
  "iin": "000000000000",
  "photo_url": null,
  "email": "",
  "school": "",
  "position": "",
  "region": "",
  "city": "",
  "subject": "",
  "experience": null,
  "lang": "ru",
  "is_admin": false,
  "onboarding_done": false,
  "created_at": "2026-08-16T09:30:00Z"
}
```

`iin` есть у всех и приходит **строкой**: ведущий ноль значащий, число его
съест. У зарегистрированных до 04.09.2026 там `000000000000` — метка
«не заполнен», настоящего такого номера не бывает. Заполненный выглядит
так же: `"iin": "909900000042"`. Подробности — раздел «Сессия
„Сертификаты 1“».

Ошибки — три состояния экрана кода:

```json
// 400 wrong_code — «Неверный код. Осталось N попытки»
{ "error": { "code": "wrong_code", "message": "Неверный код", "details": { "attempts_left": 2 } } }

// 400 code_expired — код старше 5 минут, уже использован или не запрашивался
{ "error": { "code": "code_expired", "message": "Код устарел — он действует 5 минут. Запросите новый." } }

// 429 too_many_attempts — «Ввод кода заблокирован на 10 минут»
{ "error": { "code": "too_many_attempts", "message": "Ввод кода заблокирован на 10 минут", "details": { "retry_after_sec": 600 } } }
```

## POST /auth/logout

`204`, чистит куку. Работает и без живой сессии — выход всегда успешен.

## POST /auth/logout_others

Требует входа. `200 { "revoked_count": 2 }` — сколько устройств отключено
(0 — тоже успех, кнопка на экране просто неактивна при одной сессии).

## GET /me

Требует входа. Тот же объект пользователя, что у `verify_code` (пример выше).
`401 unauthorized` — нет куки или сессия отозвана; `403 blocked` — учитель
заблокирован (действует сразу, не дожидаясь конца сессии).

## PATCH /me

Меняет только присланные поля. Строки чистятся от краевых пробелов; `null`
для строки — «стереть»; `experience` — число лет или `null`. Неизвестное
поле — 422 (защита от опечаток: `is_admin` через этот эндпоинт не меняется).

**У `iin` `null` значит «не трогать», а не «стереть»**: снять ИИН нельзя,
как и язык — по этому номеру академия вносит учителя в реестр. Значение —
ровно 12 цифр строкой, заглушку `000000000000` вписать себе руками нельзя.

`onboarding_done` у **учителя** теперь требует и ИИН: фамилии с именем мало.
У **админа** он от ИИН не зависит — админ не учится и сертификатов
не получает.

```json
// запрос — любое подмножество
{ "last_name": "Нурланова", "first_name": "Айгуль", "iin": "909900000042", "region": "Алматы", "experience": 12, "lang": "kz" }

// 200 — обновлённый пользователь целиком, onboarding_done уже true
```

ИИН уже стоит в чужом аккаунте — `409`, и **`details` пустые нарочно**: чей
это аккаунт, сервер не называет. Свой же номер занятым не считается —
повторное сохранение профиля проходит.

```json
{ "error": { "code": "iin_taken", "message": "Этот ИИН уже указан в другом аккаунте" } }
```

Не 12 цифр — `422` по полю. Подробности — раздел «Сессия „Сертификаты 1“».

## GET /me/sessions

Требует входа. Устройства с активной сессией, текущее помечено. Без
пагинации — их единицы. `device`/`browser` фронт выводит из `user_agent`;
города нет — геолокации по IP не делаем, вместо «где» показываем «когда».

```json
{
  "items": [
    {
      "id": "3f6a1c9e-8b2d-4f10-9c67-2a5b8d4e1f03",
      "created_at": "2026-08-16T09:30:00Z",
      "last_seen_at": "2026-08-16T10:02:00Z",
      "user_agent": "Mozilla/5.0 (iPhone; CPU iPhone OS 17_5 like Mac OS X) …",
      "is_current": true
    }
  ]
}

// пустого списка не бывает: без сессии эндпоинт вернёт 401
```

## DELETE /me/sessions/{id}

`204` — выход на том устройстве. `404 not_found` — чужая или уже отозванная
сессия.

## GET /dictionaries

```json
  "subjects": ["Математика", "Казахский язык и литература", "…"],
```

## GET /courses/{id}

Страница версии курса, публичная. Те же поля, что у карточки каталога, плюс
описания, чипы версий группы (только видимые в каталоге), групповой рейтинг,
программа и состояние доступа текущего пользователя. `draft` и `hidden` —
`404 not_found` для всех, включая админа (предпросмотр — отдельный режим,
позже).

`strict_order` *(добавлено в сессии 4)* — строгий порядок прохождения. При
`true` элемент программы открывается только после того, как пройден
предыдущий; при `false` порядок свободный — кроме итогового теста, он ждёт
всех уроков в любом случае. Сами статусы элементов считает
`GET /courses/{id}/program`; здесь поле затем, чтобы страница курса могла
сказать про порядок ещё до выдачи доступа.

В `program[].items` — уроки, тесты и задания модуля вперемешку по порядку;
скрытые уроки и скрытые вопросы не считаются. `kind`: `video | text` — урок
(с `duration_label`), `quiz` — тест (`questions_count`, `time_limit_min`,
`pass_score`, `is_final`), `task` — задание (`submit_format`). Пустая
`program: []` — состояние «Программа заполняется».

```json
{
  "id": 1,
  "lang": "ru",
  "title": "Критериальное оценивание в начальной школе",
  "category_id": 3,
  "cover": "https://cdn.example.kz/covers/assessment_ru.jpg",
  "hours": 72,
  "duration_text": "6 недель",
  "price": 45000,
  "status": "open",
  "starts_at": null,
  "created_at": "2026-08-10T09:30:00Z",
  "lessons_count": 18,
  "students_count": 126,
  "short": "Как ставить оценки, которым доверяют дети и родители.",
  "full": "Полный текст описания курса…",
  "versions": [
    { "id": 1, "lang": "ru", "title": "Критериальное оценивание в начальной школе", "status": "open" },
    { "id": 2, "lang": "kz", "title": "Бастауыш мектепте критериалды бағалау", "status": "open" }
  ],
  "rating": 4.5,
  "reviews_count": 2,
  "strict_order": true,
  "program": [
    {
      "id": 1,
      "title": "Модуль 1. Зачем менять оценивание",
      "items": [
        { "kind": "video", "id": 1, "title": "Что не так с пятибалльной шкалой", "time_required_min": 20, "duration_label": "14:20" },
        { "kind": "text", "id": 2, "title": "Критерии и дескрипторы", "time_required_min": 25, "duration_label": null },
        { "kind": "task", "id": 1, "title": "Составьте дескрипторы к своему уроку", "time_required_min": 40, "submit_format": "both" },
        { "kind": "quiz", "id": 1, "title": "Тест модуля 1", "time_required_min": 15, "questions_count": 8, "time_limit_min": 15, "pass_score": 70, "is_final": false }
      ]
    },
    {
      "id": 2,
      "title": "Модуль 2. Итоговая работа",
      "items": [
        { "kind": "quiz", "id": 2, "title": "Итоговый тест", "time_required_min": 40, "questions_count": 5, "time_limit_min": 40, "pass_score": 75, "is_final": true }
      ]
    }
  ],
  "access": { "state": "none" }
}
```

`access` — три состояния кнопки:

```json
// не залогинен или ни заявки, ни доступа
{ "state": "none" }

// заявка отправлена, «ждёт N дней» (дни по казахстанскому календарю)
{ "state": "requested", "waiting_days": 2 }

// доступ открыт; всё пройдено → next_lesson: null
{
  "state": "granted",
  "done_count": 6,
  "total_count": 24,
  "progress_percent": 25,
  "next_lesson": { "id": 1, "title": "Составьте дескрипторы к своему уроку", "kind": "task" }
}
```

**Изменено в сессии 4.** Счётчики считаются по **всем видимым элементам
программы** — урокам, тестам и заданиям, — а не по одним урокам: экран урока
показывает «N из M» именно так, и два разных числа на двух экранах одного курса
человек читает как ошибку. `lessons_count` при этом не меняется — это счётчик
именно уроков, и с `total_count` он теперь не совпадает.

`next_lesson` — первый непройденный элемент программы в сквозном порядке
(модули по порядку, внутри модуля — элементы по порядку), у него появился
`kind`: `video | text | quiz | task`. Без `kind` кнопка «Продолжить» не знает,
какой экран открывать: `id` у урока, теста и задания свои, и `id: 1` бывает
у всех троих. Имя поля оставлено прежним, хотя элемент может быть и тестом:
переименование сломало бы уже подключённые экраны.

Ошибки:

```json
// 404 not_found — нет курса, черновик или скрытый
{ "error": { "code": "not_found", "message": "Курс не найден" } }
```

## GET /courses/{id}/reviews

Публичный, пагинация стандартная, свежие сверху. Отзывы этой версии курса
(не группы). Сверх полей списка — `rating` (средняя) и `breakdown`
(счётчики по звёздам): оба по последнему отзыву каждого автора, а в `items`
и `total` — все строки. `author_name` собирается на сервере; `reply` пока
всегда `null` — ответу админа негде храниться (вопрос владельцу).

```json
{
  "items": [
    {
      "id": 2,
      "author_name": "Ахметова Динара",
      "school": "Гимназия №5",
      "city": "Астана",
      "rating": 4,
      "text": "",
      "created_at": "2026-08-15T14:02:00Z",
      "reply": null
    },
    {
      "id": 1,
      "author_name": "Нурланова Айгуль Сериковна",
```

## POST /admin/enrollments

Только админ, одна транзакция: создаёт `enrollment` (или снимает
`revoked_at` у отозванного — повторная выдача), закрывает открытую заявку
этой пары учитель+курс статусом `granted`, пишет учителю уведомление

```json
  "user_id": 1,
  "course_id": 1,
```

# Сессия 4 — уроки и файлы

Экраны: `/learn/{course}/{lesson}`, программа, прогресс, строгий порядок.

Здесь заканчивается прототип, где закрытый урок просто не нарисован. Всё, что
ниже, требует входа, а всё, что отдаёт содержимое курса, — ещё и **действующего
`enrollment`** по курсу этого урока (`revoked_at` пустой): без входа — `401
unauthorized`, без доступа — `403 forbidden`. Исключение одно — `POST /files`,
там достаточно входа: файл ещё ни к какому курсу не привязан. Скрытый урок (`is_hidden`) не отличается от несуществующего —
`404 not_found` для всех; то же и с невидимым курсом (`draft`, `hidden`), как
на странице курса. Порядок проверок один везде: вход, существование, доступ —
поэтому у чужого курса приходит `403`, а не `404`. Прятать за `404` тут нечего:
названия и id уроков и так лежат в `program[]` открытой страницы курса,
закрыто содержимое.

Строгий порядок — правило показа, а не защита. `status: "locked"` в программе
говорит экрану, что рисовать замок и подпись «откроется после текущего урока»;
`GET /lessons/{id}` и `playback` отдают содержимое при действующем доступе даже
у закрытого элемента. Смысл проверки на сервере в том, что платный курс
не утекает по прямой ссылке к тому, кто не платил, а не в борьбе с учителем,
который подставил в адрес id следующего урока своего же курса.

## GET /courses/{id}/program

Программа со статусами для текущего пользователя — сайдбар экрана урока.
Требует входа и действующего доступа. Модули и элементы — те же, что в
`program[]` страницы курса (`kind`, `id`, `title`, `time_required_min` и поля
по типу элемента), плюс у каждого элемента `status`. Скрытые уроки и скрытые
вопросы не показываются и в подсчётах не участвуют.

`status` — три состояния значка в сайдбаре:

- `done` — урок отмечен пройденным (`lesson_progress`); тест сдан засчитанной
  попыткой; задание зачтено. В сессии 4 данных тестов и заданий ещё нет,
  поэтому у них пока `available` или `locked`; статусы сдач фиксируются
  в сессии 5.
- `locked` — открывать нельзя.
- `available` — всё остальное.

Закрывают элемент два правила, и они складываются:

- при `strict_order: true` у курса — закрыто всё после **первого непройденного
  элемента**; сам он открыт. Порядок сквозной: модули по `order_index`, внутри
  модуля — элементы по `order_index`;
- итоговый тест (`is_final: true`) закрыт, пока не пройдены **все видимые уроки
  курса**, — независимо от `strict_order` (`BACKEND_NOTES`, раздел 4). Тесты
  модулей и задания на это не влияют: провал теста курс не блокирует.

`done` считается раньше `locked`: уже пройденный элемент закрытым не станет.

```json
// GET /courses/1/program — strict_order: true, пройдены первые два урока
{
  "program": [
    {
      "id": 1,
      "title": "Модуль 1. Зачем менять оценивание",
      "items": [
        { "kind": "video", "id": 1, "title": "Что не так с пятибалльной шкалой", "time_required_min": 20, "duration_label": "14:20", "status": "done" },
        { "kind": "text", "id": 2, "title": "Критерии и дескрипторы", "time_required_min": 25, "duration_label": null, "status": "done" },
        { "kind": "task", "id": 1, "title": "Составьте дескрипторы к своему уроку", "time_required_min": 40, "submit_format": "both", "status": "available" },
        { "kind": "quiz", "id": 1, "title": "Тест модуля 1", "time_required_min": 15, "questions_count": 8, "time_limit_min": 15, "pass_score": 70, "is_final": false, "status": "locked" }
      ]
    },
    {
      "id": 2,
      "title": "Модуль 2. Итоговая работа",
      "items": [
        { "kind": "quiz", "id": 2, "title": "Итоговый тест", "time_required_min": 40, "questions_count": 5, "time_limit_min": 40, "pass_score": 75, "is_final": true, "status": "locked" }
      ]
    }
  ]
}

// программа ещё не заполнена — то же пустое состояние, что на странице курса
{ "program": [] }

// модуль без видимых элементов остаётся в ответе с пустым items
{ "program": [ { "id": 3, "title": "Модуль 3. В работе", "items": [] } ] }
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 404 not_found — нет курса, черновик или скрытый (как у страницы курса)

// 403 forbidden — доступа к курсу нет или он отозван
{ "error": { "code": "forbidden", "message": "Доступ к курсу не открыт" } }
```

## GET /lessons/{id}

Урок целиком: то, что показывает экран `/learn/{course}/{lesson}`. Требует
входа и действующего доступа по курсу этого урока.

`body` — содержимое как оно лежит в базе, JSON без обработки. Форма содержимого
зафиксируется в сессии 7, вместе с редактором урока; до тех пор фронт получает
то, что положил админ, и в примере ниже это `{"html": "…"}`. У видеоурока `body`
может быть `null` — текст к видео необязателен.

`video_url` в ответе **нет**. Ссылку на видео выдаёт только
`GET /lessons/{id}/playback`: публичного адреса видео фронт не знает
(`BACKEND_NOTES`, раздел 9).

`files` — материалы урока по `order_index`; ссылки в списке тоже нет, за ней
идут отдельно в `GET /files/{id}`, когда человек нажал на файл. Нет
материалов — `[]`, это нарисованное пустое состояние, а не отсутствие блока.

```json

  ]
}

// 200 — текстовый урок без материалов
{
  "id": 2,
  "module_id": 1,
  "title": "Критерии и дескрипторы",
  "kind": "text",
  "body": { "html": "<h2>Дескриптор — это наблюдаемое действие</h2>…" },
  "duration_label": null,
```

```json
{ "error": { "code": "forbidden", "message": "Урок откроется после выдачи доступа к курсу" } }
```

## POST /lessons/{id}/complete

Отметка «урок пройден». Требует входа и действующего доступа, тело пустое:
что именно отмечено, сказано в пути. **Идемпотентен** — повторный вызов
не ошибка, `completed_at` остаётся временем первой отметки. Снять отметку
нельзя, эндпоинта нет: «12 из 18» не должно уезжать назад ни по кнопке,
ни по двойному клику.

В ответе — блок прогресса курса, тот же, что в `access.granted`. Не `204`
осознанно: экран урока сразу перерисовывает «N из M» и кнопку «Далее», не
дожидаясь ответа на второй запрос. За программой фронт всё же сходит отдельно,
когда `strict_order` открыл следующий элемент и в сайдбаре надо снять замок.

```json
// 200
{
  "is_completed": true,
  "done_count": 7,
  "total_count": 24,
  "progress_percent": 29,
  "next_lesson": { "id": 1, "title": "Составьте дескрипторы к своему уроку", "kind": "task" }
}

// 200 — отмечен последний непройденный элемент курса
{ "is_completed": true, "done_count": 24, "total_count": 24, "progress_percent": 100, "next_lesson": null }
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 404 not_found — нет урока или он скрыт

// 403 forbidden — доступа к курсу нет или он отозван
{ "error": { "code": "forbidden", "message": "Урок откроется после выдачи доступа к курсу" } }
```

## GET /lessons/{id}/playback

Ссылка для плеера. Требует входа и действующего доступа, и доступ проверяется
**на каждый вызов**: если админ отозвал его посреди просмотра, следующий запрос
вернёт `403`, а не новую ссылку.

Сейчас `video_provider = youtube`: своего видеохостинга нет, отдаётся тот же
адрес, что лежит в `lesson.video_url`, и `expires_at: null` — эта ссылка
не протухает. Форма ответа заранее сделана под свой хостинг: там в `url` придёт
подписанная ссылка на раздатчик, а в `expires_at` — настоящее время истечения
(TTL 15 минут), `provider` сменится вместе с `lesson.video_provider`. Плеер
из-за этого переделывать не придётся — он и сегодня ходит через `playback`,
а не за `video_url`.

Два разных отказа, и путать их нельзя (`BACKEND_NOTES`, раздел 9):

- **подпись протухла** — это откажет раздатчик на самой ссылке, а не этот
  эндпоинт. Плеер молча просит `playback` заново и продолжает с той же секунды.
  Сегодня, на YouTube, такого случая нет вовсе;
- **доступ закрыт** — `403` от этого эндпоинта. Повторять нечего, на экране
  состояние «не удалось продолжить».

Лимит частоты — 10 запросов в минуту на пользователя: без него эндпоинт
превращается в удобную качалку.

```json
// 200 — пока провайдер youtube
{ "provider": "youtube", "url": "https://www.youtube.com/watch?v=kZ3vX1a9Qd0", "expires_at": null }
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 404 not_found — нет урока, он скрыт или у урока нет видео (kind: "text")

// 403 forbidden — доступа к курсу нет или он отозван
{ "error": { "code": "forbidden", "message": "Доступ к курсу закрыт" } }

// 429 rate_limited — слишком часто просят ссылку
{ "error": { "code": "rate_limited", "message": "Слишком много запросов — попробуйте через несколько секунд", "details": { "retry_after_sec": 12 } } }
```

## POST /files

Загрузка файла в приватное хранилище. Требует входа. `multipart/form-data`
с одним полем `file`, лимит размера — 20 МБ. Хранилище приватное и лежит
за портом `storage`: публичный бакет означает, что материалы платного курса
попадут в поиск.

Это инфраструктура под сессии 5 и 7 — сдачи работ и материалы уроков. Сам
по себе загруженный файл ни к чему не привязан: привязка происходит в том
запросе, куда `key` передаётся дальше.

В ответе **`key`, а не `id`**: строки в базе за загруженным файлом ещё нет,
и таблицы под неё нет тоже. `key` — путь объекта в приватном хранилище, и
именно он хранится в `lesson_file.url` и в `submission.files[].url`; публичного
адреса в базе не появляется нигде. Наружу `key` уходит только тому, кто прямо
сейчас загрузил файл, чтобы передать его в следующий запрос; в ответах, которые
показывают уже сохранённые файлы, ключа нет — там `id` строки, а байты
достаются подписанной ссылкой.

`name` — имя, как его прислал браузер, очищенное от путей; `mime` определяется
на сервере, а не берётся из запроса. Ограничение по расширениям здесь не
проверяется: список `allowed_ext` живёт у задания и проверяется при сдаче
работы, в сессии 5.

```json
// запрос — multipart/form-data, поле file

// 200
{
  "key": "uploads/2026/08/18/9f3c1a7e4b2d8c05.pdf",
  "name": "Памятка по критериям.pdf",
  "size_bytes": 184320,
  "mime": "application/pdf"
}
```

Ошибки:

```json
// 401 unauthorized — не залогинен

// 413 file_too_large — файл больше лимита
{ "error": { "code": "file_too_large", "message": "Файл больше 20 МБ", "details": { "max_size_mb": 20 } } }

// 422 validation_error — поля file нет или файл пустой
{ "error": { "code": "validation_error", "message": "Файл не выбран", "details": { "fields": [ { "field": "file", "message": "Field required" } ] } } }
```

## GET /files/{id}

`id` здесь — `lesson_file.id`, то есть материал урока. Требует входа
и действующего доступа по курсу этого урока.

Отдаёт подписанную ссылку с коротким сроком жизни (15 минут, как у видео):
путь, время истечения и подпись на серверном секрете. Байты раздаёт отдельный
путь, который проверяет подпись сам, до отдачи файла — в бою это `secure_link`

админ, — и она появится в сессии 5.

```json
  "expires_at": "2026-08-18T09:45:00Z"
}
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 404 not_found — нет такого файла или урок скрыт
```

# Сессия 5 — тесты и задания

Экраны: `/learn/{course}/quiz/{id}` — прохождение, результат, разбор;
`/learn/{course}/task/{id}` — задание; `/submissions` в админке — очередь
проверки.

Рамка доступа — та же, что у уроков: всё требует входа и действующего
`enrollment` по курсу элемента; админские эндпоинты вместо этого требуют
`is_admin`. Порядок проверок прежний: вход, существование, доступ. Своего
`is_hidden` у теста и задания нет — `404 not_found` приходит, когда записи
нет или курс невидим (`draft`, `hidden`). Замок строгого порядка (`locked`
в программе) — правило показа, не защита: при действующем доступе тест
и задание отдаются и по прямой ссылке, как уроки.

Три решения держат всю сессию:

- **Одна попытка держится базой, а не кодом.** Частичный уникальный индекс
  `(user_id, quiz_id) WHERE is_counted` пропускает одну зачётную попытку
  на тест. У непересдаваемого теста попытка создаётся сразу зачётной
  (`is_counted: true`) — вторую база не даст вставить, даже двойным кликом.
  У пересдаваемого новая попытка создаётся незачётной, а зачётность
  переключается на неё в транзакции `finish`: зачётная — **последняя
  завершённая**, незавершённая попытка зачёт не трогает. Активная попытка
  тоже одна и тоже держится индексом — `(user_id, quiz_id) WHERE
  finished_at IS NULL`. Хранятся все попытки, всегда.
- **Время считает сервер.** `started_at` живёт в базе, клиент получает
  `remaining_sec` и рисует таймер от него. После истечения времени ответы
  не принимаются, а `finish` работает всегда и считает по сохранённому.
- **Статусы сдачи задания**: `pending` («на проверке») → `accepted`
  («зачтено») или `rework` («на доработку»). Других не бывает. Каждая
  отправка — новая строка, история не переписывается.

Действующая строка сертификата по курсу закрывает новые попытки любого теста
этого курса, даже у пересдаваемого: результат не должен меняться под уже
выданным документом. **Заявка закрывает их так же** — админ выпишет бумагу
по чек-листу, который был проверен в момент запроса. Разбор при этом остаётся
доступным, а отзыв строки тесты снова открывает.

## GET /quizzes/{id}

Тест для текущего пользователя: правила — и состояние, из которого экран
выбирает, что рисовать. Требует входа и действующего доступа.

Вопросы наружу уходят **только внутри активной попытки**: до старта экран
видит числа (`questions_count`, `time_limit_min`, `pass_score`), а не
вопросы — иначе тест можно изучить, не тратя единственную попытку.
Правильные ответы не уходят никогда, вплоть до разбора. `max_score` —
сумма баллов видимых вопросов; скрытые (`is_hidden`) не показываются
и не считаются.

`state.status` — три состояния экрана:

- `not_started` — стартовая карточка. `can_start: false`, когда по курсу
  есть действующая строка сертификата — **заявка или выданный документ** —
  либо тест закрыт замком программы;
- `in_progress` — есть незавершённая попытка, экран продолжает её.
  `attempt` — та же форма, что ответ `POST /quizzes/{id}/quiz_attempts`,
  с вопросами, сохранёнными ответами и `remaining_sec`. Активная попытка
  главнее прочих состояний;
- `finished` — активной нет, завершённые есть. `result` — зачётная
  попытка, форма как у ответа `finish`. `can_retake: true` — только
  у пересдаваемого теста, если по курсу нет действующей строки сертификата
  (ни заявки, ни документа) и тест не закрыт замком программы.
  `review_available` — можно ли открыть разбор: у непересдаваемого всегда
  `true`, у пересдаваемого — по настройке `show_review`.

`attempts` — история завершённых попыток, старые сверху, зачётная помечена
`is_counted`. Незавершённой попытки здесь нет — она в `state`.

## POST /quizzes/{id}/quiz_attempts

Начинает попытку. Требует входа и действующего доступа, тело пустое.
Время пошло на сервере с этого момента.

Порядок вопросов фиксируется здесь: при `shuffle` — перемешивается
и запоминается в попытке, чтобы разбор показал ровно то, что человек
видел. Варианты внутри вопроса идут по своему порядку, они не мешаются.
`remaining_sec: null` — у теста нет лимита времени.

**Идемпотентен по активной попытке**: если незавершённая попытка уже есть,
возвращается она же — с сохранёнными ответами и оставшимся временем.
Двойной клик по «Начать тест» не тратит вторую попытку: у непересдаваемого
её не пропустит индекс, и сервер в этом случае тоже отвечает уже созданной
попыткой.

## POST /quiz_attempts/{id}/answers

Сохраняет ответ на один вопрос — по одному и сразу, как только человек
его выбрал: при единственной попытке потеря ответов недопустима. Повторный
ответ на тот же вопрос **заменяет** прежний; пустой `option_ids` снимает
ответ. Менять можно до `finish`.

`single` и `bool` принимают не больше одного варианта. Вопрос не из этой
попытки или чужой вариант — `422`.

Чужая попытка — `404`: попытки личные, их id не публикуются.

```json
// запрос
{ "question_id": 5, "option_ids": [21] }

// 204
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 404 not_found — нет попытки или она чужая
// 403 forbidden — доступ к курсу отозван посреди попытки

// 409 attempt_finished — попытка уже завершена
{ "error": { "code": "attempt_finished", "message": "Попытка уже завершена" } }

// 409 time_expired — время вышло; ответ не сохранён, фронт зовёт finish
{ "error": { "code": "time_expired", "message": "Время истекло — ответы отправлены на подсчёт" } }

// 422 validation_error — вопрос не из попытки, вариант не из вопроса,
// два варианта у single
{ "error": { "code": "validation_error", "message": "Проверьте заполнение полей", "details": { "fields": [ { "field": "option_ids", "message": "Вопрос принимает один вариант ответа" } ] } } }
```

## POST /quiz_attempts/{id}/finish

Завершает попытку и считает результат. Требует входа и действующего
доступа, тело пустое. **Идемпотентен**: повторный вызов возвращает тот же
результат — двойной клик по «Завершить тест» не ошибка.

Если время вышло, `finished_at` ставится равным `started_at + лимит`,
`timed_out: true`, счёт идёт по сохранённым ответам — это и есть
«автосдача»: фронт зовёт `finish`, когда его таймер дошёл до нуля или
`answers` ответил `time_expired`.

Счёт: вопрос закрыт верно — только если выбран **полностью правильный
набор** вариантов, частичных баллов нет. `score_percent` — процент от
`max_score`, округлённый до целого; `passed` — `score_percent >=
pass_score`. Балл и состав вопросов попытки зафиксированы — задним числом
они не пересчитываются.

У пересдаваемого теста здесь же, в одной транзакции, зачёт переключается
на эту попытку: прежняя зачётная становится `is_counted: false`. Статус
теста в программе следует за зачётной попыткой: пересдал хуже проходного —
`done` у элемента пропадает.

```json
// 200
{
  "id": 12,
  "score": 7,
  "max_score": 10,
  "score_percent": 70,
  "pass_score": 70,
  "passed": true,
  "is_counted": true,
  "timed_out": false,
  "minutes_spent": 12,
  "review_available": true
}
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 404 not_found — нет попытки или она чужая
// 403 forbidden — доступ к курсу отозван посреди попытки
```

## GET /tasks/{id}

Задание целиком: условие и состояние сдач текущего пользователя. Требует
входа и действующего доступа.

`statement` — содержимое как лежит в базе, JSON без обработки, как `body`
урока: форма зафиксирована в сессии 7а. `template_file`
— файл-шаблон или `null`; ссылка на скачивание — отдельным запросом ниже,
по клику. **Изменено в сессии 7а:** `template_file.name` — имя, под которым
файл приложил админ, а не имя объекта в хранилище: ключи там случайные,

## POST /tasks/{id}/submissions

Сдача работы. Требует входа и действующего доступа. Файлы сначала
загружаются по одному через `POST /files`, сюда приходят их `key` и имя,
под которым файл показывать; сервер сам определяет размер и mime по
хранилищу и кладёт в сдачу снимок метаданных — `key` наружу больше
не возвращается.

Проверки здесь, а не при загрузке: расширение каждого файла — из
`allowed_ext` задания (пустой список — любое), размер — не больше
`max_size_mb`, файлов — не больше 10. `submit_format` решает состав:
`text` — только текст, `file` — только файлы, `both` — что-то одно или
всё сразу; пустая сдача не принимается. Ответ — созданная сдача в форме
элемента истории.

Одновременно живёт одна работа: пока сдача `pending`, новая не
принимается; после `accepted` задание закрыто совсем. После записи в базу
админам уходит Telegram-уведомление — «Работа №4 на проверку: задание
„Составьте дескрипторы…“, курс „Критериальное оценивание…“», без ФИО,
как у заявок; недоступность бота сдачу не ломает.

## Файлы сдач — GET /files/submission/{submission_id}/{index}/{name}

Байты файла сдачи. Это ссылка из `files[].url`, фронт её не строит.
В отличие от материалов урока подпись не используется: проверка — **сессия**,
файл отдаётся автору сдачи и админам, ссылка постоянная и не протухает.
`index` — позиция файла в сдаче, `{name}` в пути — только для имени
при сохранении.

Ошибки: `401 unauthorized` — без входа, `403 forbidden` — не автор
и не админ, `404 not_found` — нет сдачи или файла с таким номером.

## GET /admin/submissions

Только админ (`403 forbidden` для остальных). Очередь проверки: пагинация

## POST /admin/submissions/{id}/review

Вердикт. Только админ. `verdict` — `accepted` или `rework`; `comment`
при `rework` обязателен (на экране это подсказка учителю, что доделать),
при `accepted` — по желанию. Одна транзакция: статус, комментарий,
`reviewed_by` (кто из админов проверил — в базу, наружу учителю
не уходит), `reviewed_at`, плюс уведомление учителю в колокольчик
(`submission_reviewed`, эндпоинты колокольчика — сессия 6, запись — уже
сейчас, как `access_granted`).

Вердикт ставится один раз: проверенная работа не перепроверяется —
`409`. Передумал — учитель пришлёт доработку, у неё будет свой вердикт.
После `accepted` элемент программы становится `done`, это видно
в `GET /courses/{id}/program` и прогрессе курса.

«Сохранить и перейти к следующей» — навигация фронта по уже загруженной
очереди, отдельного эндпоинта нет. Ответ — обновлённая карточка, форма
как у `GET /admin/submissions/{id}`.

```json
// запрос — зачесть; comment можно не присылать
{ "verdict": "accepted" }

// запрос — на доработку
{ "verdict": "rework", "comment": "Добавьте по одному дескриптору на каждый критерий." }

// 200 — карточка целиком (форма как в GET /admin/submissions/{id})
```

Ошибки:

```json

// 409 already_reviewed — вердикт уже стоит
{ "error": { "code": "already_reviewed", "message": "Работа уже проверена" } }

// 422 validation_error — rework без комментария
{ "error": { "code": "validation_error", "message": "Проверьте заполнение полей", "details": { "fields": [ { "field": "comment", "message": "При отправке на доработку комментарий обязателен" } ] } } }
```

# Сессия 6 — сертификаты и остальное

Условия сертификата стали **настройкой курса**: четыре флага в таблице `course`
(`cert_require_lessons`, `cert_require_tasks`, `cert_require_module_quizzes`,
`cert_require_final_quiz`). Редактор для них — сессия 7; пока значения ставятся
в базу. Курс, где не включён ни один флаг, пускает к заявке сразу после выдачи
доступа — так обещает бриф; сам документ по ней выписывает админ (раздел
«Сессия „Сертификаты 1“»).

Проходной балл остаётся у теста (`quiz.pass_score`), у курса своего балла нет:
экран результата теста и чек-лист сертификата всегда показывают одно число.
Поэтому в строке «Сдать все тесты модулей» процента нет — у каждого теста
модуля он свой.

## GET /courses/{id}/completion

Чек-лист условий сертификата. Публичный, как и сама страница курса: без входа
и без доступа отдаётся **список требований без счётчиков** (`done_count: null`)
— бриф так и говорит: «до выдачи доступа просто список требований, после —
живой прогресс». `draft` и `hidden` — `404`, как у страницы курса.

В `conditions` только включённые у курса условия, в порядке чек-листа. `status`:
`not_started | in_progress | done`. `total_count` считается по видимым элементам
программы, как и везде: скрытый урок в условие не входит.

**Условие, под которым нет ни одного элемента, выполненным не считается**
(`total_count: 0` → `not_started`). Иначе флаг, выставленный до наполнения
курса, раздал бы сертификаты всем; а урок с чьим-то прогрессом не удаляют,
а скрывают — и скрытие последнего непройденного урока схлопнуло бы условие
в выполненное. Курс совсем без условий — другой случай: там `conditions: []`,
и попросить сертификат правда можно сразу.

`blocker` — почему кнопка запроса не активна, **хотя условия выполнены**. Сейчас
он один: по курсу идёт незавершённая попытка теста, её `finish` ещё может
поменять зачёт. `null` — помех нет. Пока чек-лист не закрыт, `blocker` всегда
`null`: человеку, у которого пройдено 12 уроков из 18, надо показать чек-лист,
а не «завершите начатый тест».

`can_request` — можно ли **попросить** документ: выписывает его админ, а кнопка
на экране называется «Запросить сертификат». `certificate` — **состояние
строки**, а не выданный документ: `id`, `status` (`requested` — заявка,
`issued` — документ), `number`, `requested_at` и `issued_at`. Поданная заявка
гасит кнопку так же, как гасил выданный документ: просить дважды нечего.
Отозванная строка сюда не приходит — после отзыва человек может попросить
снова. Подробности — раздел «Сессия „Сертификаты 1“».


## POST /courses/{id}/certificate

**Создаёт заявку** на сертификат — сам документ по ней выпишет админ руками
(раздел «Сессия „Сертификаты 1“»). Требует входа и действующего доступа.
Тела запроса нет.

Ручка висит на кнопке «Запросить сертификат». При открытии экрана дёргать её
не нужно и нельзя: состояние строки приходит в `GET /courses/{id}/completion`,
а вызов отсюда завёл бы заявку каждому, кто просто открыл адрес.

**Идемпотентно:** повторный вызов возвращает `200` и **ту же** строку — заявку
или уже выданный документ, а не ошибку. Единственность держится частичным
уникальным индексом `uq_certificate_active (user_id, course_id, platform)
WHERE revoked_at IS NULL` — двойной клик даёт одну заявку, а не две. Второго
сообщения в Telegram повтор не шлёт.

**`enrollment.completed_at` здесь не проставляется** — его ставит выдача
админом (`POST /admin/certificates/{id}/issue`). «Курс пройден» и «сертификат
выдан» по-прежнему одно событие, и вкладка «Пройденные» на `/my` держится
на нём, но наступает оно теперь у админа, а не в момент заявки.

Ответ — состояние строки, той же формы, что `certificate` в `completion`.
Снимки для бумаги (`holder_name`, `course_title`, `hours`, `lang`) снимаются
здесь же, в момент заявки, но в этот ответ не идут: их видит админ в своём
списке. `lang` — язык версии курса; сертификат одноязычный (`BACKEND_NOTES`,
раздел 3), и переключателя языков у него нет.

```json
// 200 — заявка создана только что или уже стояла
{
  "id": 7,
  "status": "requested",
  "number": null,
  "requested_at": "2026-08-19T07:10:00Z",
  "issued_at": null
}
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 404 not_found — нет курса, черновик или скрытый

// 403 forbidden — доступа к курсу нет или он отозван
{ "error": { "code": "forbidden", "message": "Доступ к курсу не открыт" } }

// 409 conditions_not_met — условия ещё не выполнены; в details тот же чек-лист,
// что отдаёт GET /courses/{id}/completion, чтобы экран показал, чего не хватает
{
  "error": {
    "code": "conditions_not_met",
    "message": "Условия сертификата ещё не выполнены",
    "details": {
      "conditions": [
        { "code": "lessons", "label": "Пройти все уроки", "status": "in_progress", "done_count": 12, "total_count": 18 }
      ]
    }
  }
}

// 409 attempt_in_progress — по курсу идёт незавершённая попытка теста
{
  "error": {
    "code": "attempt_in_progress",
    "message": "Завершите начатый тест — он ещё может изменить зачёт"
  }
}

// 409 profile_incomplete — в профиле не заполнены фамилия и имя
{
  "error": {
    "code": "profile_incomplete",
    "message": "Заполните фамилию и имя — они печатаются на сертификате"
  }
}

// 409 iin_required — в профиле не заполнен ИИН; самого номера в отказе
// нет и быть не может
{
  "error": {
    "code": "iin_required",
    "message": "Заполните ИИН — без него сертификат не выдать"
  }
}
```

Порядок проверок: доступ → условия → незавершённая попытка → профиль → ИИН.
Условия раньше попытки затем, чтобы отказ показывал чек-лист, а не частность
про тест. Повтор проверяется раньше всех них: у того, кто уже попросил, ответ
один и тот же независимо от того, что с тех пор поехало.

`profile_incomplete` нужен потому, что вход по SMS заводит человека с пустым
именем, а `holder_name` — снимок: поправить профиль постфактум выданный
документ не изменит, его пришлось бы отзывать и выдавать заново. Особенно
легко поймать на курсе без единого условия — там заявку можно подать в ту же
секунду, что и доступ, то есть раньше, чем человек открыл профиль.

## GET /me/certificates

Мои сертификаты, свежие сверху. Требует входа. Без пагинации: список
заведомо короткий, экран `/certificates` её и не рисует.

**Экран `/certificates/{id}` живёт этим же ответом** — отдельного эндпоинта
за одним сертификатом нет: в элементе уже есть всё, что печатает макет,
включая `holder_name`. Отозванные (`revoked_at`) в список не попадают,
и **заявки тоже**: пока админ не выписал документ, печатать нечего, а своё
ожидание человек видит на экране курса.

`registration_number` — номер академии, второй номер на бумаге. У документов
до 04.09.2026 он пустая строка, пока админ не проставит его руками.

```json
{

{ "items": [] }
```

## GET /verify/{number}

**Публичный, без входа** — комиссия проверяет документ, не заводя аккаунта.

Номер нормализуется на сервере: регистр и дефисы можно не соблюдать,
`kz2026xb7k2m` находит `KZ-2026-XB7K2M`. Формат — `KZ-{год}-{6 символов}`,
алфавит из 32 знаков без похожих начертаний (нет `0`, `O`, `1`, `I`):
последовательный номер перебирается скриптом за минуту, случайный из миллиарда
вариантов — нет (`BACKEND_NOTES`, раздел 6).

**В ответе только то, что напечатано на бумаге.** Ни `user_id`, ни `course_id`,
ни `id` сертификата, ни ссылок в кабинет: страница публичная, а школа, регион
и телефон учителя к проверке подлинности отношения не имеют. **ИИН здесь нет
и не будет** — по той же причине: адрес открывает посторонний человек.

Номеров на странице два, и они стоят рядом: наш `number` и
`registration_number` академии — комиссии второй полезнее первого. У документов
до 04.09.2026 `registration_number` пустой. Заявка сюда не попадает
по построению: номера у неё нет.

```json
// 200 — подлинный
{
  "status": "valid",
  "number": "KZ-2026-XB7K2M",
  "registration_number": "АО-2026/0417",
  "holder_name": "Смагулова Гульмира Токтарбековна",
  "course_title": "Критериальное оценивание в начальной школе",
  "hours": 72,
  "issued_at": "2026-03-02T07:15:00Z",
  "revoked_at": null
}

// 200 — отозван: запись в реестре есть, но документ недействителен
{
  "status": "revoked",
  "number": "KZ-2026-XB7K2M",
  "registration_number": "АО-2026/0417",
  "holder_name": "Смагулова Гульмира Токтарбековна",
  "course_title": "Критериальное оценивание в начальной школе",
  "hours": 72,
  "issued_at": "2026-03-02T07:15:00Z",
  "revoked_at": "2026-05-11T09:00:00Z"
}
```

Ошибки:

```json

{ "error": { "code": "not_found", "message": "Сертификат не найден" } }

// 429 rate_limited — перебор номеров с одного адреса
{
  "error": {
    "code": "rate_limited",
    "message": "Слишком много проверок, попробуйте позже",

  }
```

## GET /notifications

Колокольчик учителя. Требует входа, пагинация стандартная, свежие сверху.
Непрочитанные наверх **не поднимаются** — порядок только по времени.

Сверх страницы — `unread_count`: он нужен шапке на каждом экране, а не только
на `/notifications`. Выпадающая панель колокольчика берёт `?per_page=4` и
получает и четыре верхних уведомления, и счётчик, одним запросом.

В базе хранится `type` и `params`, готовый текст не хранится: учитель
переключит язык — старые уведомления должны стать казахскими
(`BACKEND_NOTES`, раздел 11). Поэтому `text` **собирается в момент чтения**
по `user.lang` и приходит готовой строкой, а `params` отдаются рядом — из них
фронт строит адрес перехода. Правило не нарушено: в базе по-прежнему лежит
`type` и `params`.

Типы и что лежит в `params`:

| `type` | Когда | `params` |
|---|---|---|
| `access_granted` | админ выдал доступ к курсу | `course_id`, `course_title` |
| `submission_reviewed` | админ проверил работу | `task_id`, `task_title`, `course_id`, `verdict` (`accepted \| rework`) |
| `answer_posted` | кто-то ответил на вопрос учителя под уроком | `lesson_id`, `lesson_title`, `course_id`, `message_id` |
| `certificate_issued` | сертификат выдан | `course_id`, `course_title`, `certificate_id` |
| `retake_allowed` | админ разрешил пересдачу теста (**добавлен в сессии 7б**) | `course_id`, `quiz_id`, `quiz_title` |

```json
// GET /notifications?page=1&per_page=20
{
  "items": [
    {
      "id": 42,
      "type": "answer_posted",
      "text": "Администратор ответил на ваш вопрос к уроку «Критерии и дескрипторы»",
      "params": { "lesson_id": 2, "lesson_title": "Критерии и дескрипторы", "course_id": 1, "message_id": 18 },
      "read_at": null,
      "created_at": "2026-08-19T06:40:00Z"
    },
    {
      "id": 41,
      "type": "submission_reviewed",
      "text": "Ваше задание «Составьте дескрипторы к своему уроку» зачтено",
      "params": { "task_id": 1, "task_title": "Составьте дескрипторы к своему уроку", "course_id": 1, "verdict": "accepted" },
      "read_at": "2026-08-19T06:00:00Z",
      "created_at": "2026-08-18T11:20:00Z"
    }
  ],
  "unread_count": 1,
  "total": 12,
  "page": 1,
  "per_page": 20
}

// уведомлений нет
{ "items": [], "unread_count": 0, "total": 0, "page": 1, "per_page": 20 }
```

## POST /notifications/read

Отмечает прочитанными. Требует входа, отвечает `204`. Ровно одно из двух полей:

```json
// одно или несколько — клик по уведомлению
{ "ids": [42, 41] }

// все — кнопка «Отметить все как прочитанные»
{ "all": true }
```

В `ids` не больше 100 значений — столько же, сколько на самой длинной странице
списка. Чужие и несуществующие `id` молча пропускаются: список у учителя мог
устареть, и отметка «прочитано» — не то место, где стоит показывать ошибку. Уже
прочитанное второй раз не переписывается — `read_at` остаётся первым.

Ошибки:

```json
// 401 unauthorized — не залогинен

// 422 validation_error — оба поля сразу или ни одного
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "ids", "message": "Нужно указать ids или all" } ] }
  }
}
```

## GET /lessons/{id}/questions

Вопросы под уроком. Требует входа и действующего доступа по курсу этого урока —
те же правила, что у самого урока. Пагинация стандартная, свежие сверху;
ответы внутри треда — по возрастанию времени.

Тред ровно в два уровня: вопрос и плоский список ответов. Второго уровня
вложенности нет и не будет (`DESIGN_BRIEF`, «Чего не делаем»).

включая отчество, если оно заполнено. Инициалы для аватара фронт считает сам. `author_is_admin`
нужен для синей подписи и бейджа «Администратор»; отдельной колонки под это
нет — берётся из `user.is_admin` в момент чтения.

## POST /lessons/{id}/questions

Новый вопрос или ответ в треде — **один эндпоинт на оба действия**, различает
их `parent_id`. Требует входа и действующего доступа. Отвечает `201` с
созданным сообщением в той же форме, что элемент списка (у ответа `replies`
нет).

Отвечать может админ **и любой учитель с доступом к курсу** — «часто коллега
отвечает быстрее, и ответ видят все остальные» (`DESIGN_BRIEF`). Отдельного
права на ответ нет.

`parent_id` проверяется на сервере: он должен быть корневым сообщением
**этого же урока**. Ответ на ответ — `422`, а не молчаливое создание третьего
уровня. Автору корня уходит уведомление `answer_posted`; на собственный ответ
уведомление не приходит.

Лимит частоты — три сообщения в минуту: форма без капчи открыта для спама
изнутри курса. **На админа лимит не действует** — он отвечает из очереди
вопросов и упёрся бы в него на четвёртом ответе подряд. Действующий доступ
к курсу админу тоже не нужен: у него `enrollment` по курсу обычно нет,
а отвечать он должен везде. Видимость при этом действует и для него — вопрос
под скрытым уроком даёт `404`.

```json
// запрос — новый вопрос
{ "text": "А если в классе 34 человека, дескрипторы на каждого реально успеть?", "parent_id": null }

// запрос — ответ в треде
{ "text": "Успеть — да, если писать дескрипторы на группу.", "parent_id": 5 }

// 201 — ответ
{
  "id": 7,
  "text": "Успеть — да, если писать дескрипторы на группу.",
  "author_name": "Смагулова Гульмира",
  "author_is_admin": false,
  "created_at": "2026-08-19T07:30:00Z",
  "replies": []
}
```

Ошибки:

```json
// 401 unauthorized, 403 forbidden, 404 not_found — как у GET

// 422 validation_error — пустой текст, длиннее 2000 символов
// либо parent_id указывает не на корень этого урока
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "parent_id", "message": "Отвечать можно только на вопрос" } ] }
  }
}

// 429 rate_limited — форма без капчи, лимит на пользователя
{
  "error": {
    "code": "rate_limited",
    "message": "Слишком часто, попробуйте позже",
    "details": { "retry_after_sec": 20 }
  }
}
```

## GET /admin/questions

Сводная очередь вопросов по всей платформе — экран «Вопросы от учителей».
**Этого эндпоинта не было в плане сессии**: собрать очередь из
`GET /lessons/{id}/questions` нельзя, админ не знает заранее, у каких уроков
есть вопросы.

Только админ (`403 forbidden` для остальных). Пагинация стандартная, свежие
сверху. Фильтры: `answered` (`false` — только без ответа, экран открывается
именно так), `course_id`, `q` — поиск по тексту вопроса и ФИО автора.

«Без ответа» — это «никто ещё не ответил», а не «в треде появилась вторая
строка»: ответ автора самому себе вопрос из очереди не убирает, иначе учитель
снимал бы свой же вопрос, дописав к нему уточнение.

`teacher` отдаётся разложенным на части, как в заявках и очереди работ: ФИО
собирает фронт. `lesson.number` — сквозной номер среди видимых уроков курса,
из него строится подпись «Урок 6 · Создание теста за 10 минут». У вопроса под
уроком, который потом скрыли, номера не существует — приходит `0`.

```json
// GET /admin/questions?answered=false&page=1&per_page=20
{
  "items": [
    {
      "id": 4,
      "text": "Где взять примеры дескрипторов по естествознанию?",

      "teacher": {
        "id": 12,
        "last_name": "Ахметова",
        "first_name": "Динара",
        "middle_name": "Сериковна"
      },
      "course": { "id": 1, "title": "Критериальное оценивание в начальной школе" },
      "lesson": { "id": 2, "number": 6, "title": "Создание теста за 10 минут" },
      "replies": []
    }
  ],
  "total": 2,
  "page": 1,
  "per_page": 20
}

// очередь пуста
{ "items": [], "total": 0, "page": 1, "per_page": 20 }
```

Отвечает админ тем же `POST /lessons/{id}/questions` — `lesson.id` для этого
и лежит в ответе.

## GET /admin/overview

Дашборд админа. Только админ. Одним ответом — четыре счётчика «требует
действия», три коротких списка под ними и справочные числа внизу экрана.
Считается в момент запроса, ничего не кэшируется (`BACKEND_NOTES`, раздел 13).

Списки — по 5 элементов, одинаково у всех трёх. Счётчики `*_count` — полные,
их же показывают бейджи меню: два запроса, которыми шапка админки сейчас
тянет `total` у `/admin/leads` и `/admin/submissions`, этим ответом
закрываются.

`certificates_count` — четвёртая очередь: заявки на сертификат, ждущие выдачи.
**Списка под ним нет** — экран рисует три списка, четвёртый никто не просил
(подробности — раздел «Сессия „Сертификаты 1“»).

`waiting_days` — целые дни по казахстанскому календарю, как везде. Порог,
после которого число краснеет, — забота фронта: у заявок он свой, у работ свой.

Справочные числа: `teachers` — все, у кого не стоит `is_admin`
(заблокированные тоже учителя); `courses_published` — версии курсов, видимые
в каталоге (`planned | open | closed`); `certificates` — выданные и не
отозванные документы, заявки в это число не входят.

Графиков, периодов, «активных за месяц» и среднего прогресса по платформе
здесь нет и не будет (`BACKEND_NOTES`, раздел 13).

```json
      "course": { "id": 1, "title": "Критериальное оценивание в начальной школе" }

  "submissions": [
    {
      "id": 8,
```

## GET /admin/reports/{course_id}

Отчёт по версии курса. Только админ. Сводка и воронка приходят целиком,
участники — постраничным списком внутри того же ответа: на экране их 812,
и отдавать всех разом нельзя. Пагинация и поиск — стандартные
(`?page=&per_page=&q=`), `q` ищет по ФИО.

`generated_at` — момент запроса: отчёт считается на лету и нигде не хранится.

Сводка:

- `granted` — доступов, не отозванных;
- `started` — из них те, у кого есть хоть один пройденный элемент программы;
- `completed` — `enrollment.completed_at` проставлен;
- `avg_progress_percent`, `avg_final_score` — округлённые до целого; `null`,
  если считать не по кому;
- `certificates` — действующие сертификаты по этой версии курса;
- `avg_days_to_complete` — среднее число дней от выдачи доступа до завершения,
  `null`, если никто не завершил.

сколько учителей этот элемент **прошли**. Не выборка: элементы все, решение,
какие показать, принимает экран. Пояснительных выводов («стоит проверить
формулировку условия») сервер не даёт — это текст экрана.

## POST /admin/preview/enter, POST /admin/preview/exit

Режим «Предпросмотр как учитель». Только админ, оба отвечают `204`.
`?preview=1` в адресе был времянкой прототипа — флаг переезжает в серверную
сессию (`BACKEND_NOTES`, раздел 12).

```json
// запрос enter
{ "course_id": 1 }
```

Режим привязан к курсу, а не к кабинету целиком: админ пришёл смотреть
конкретный курс, и незачем распространять «ничего не сохраняется» на всё
остальное. `exit` тела не имеет и **идемпотентен** — повторный вызов вне
режима тоже `204`: кнопку «Выйти» нажимают дважды.

Пока режим включён:

- **все записи по этому курсу — no-op.** Отметка урока, ответы теста, сдача
  задания, заявка на сертификат, уведомления, отзыв, вопрос под уроком и
  загрузка файла. Ответ у них обычный, успешный, но в базе не остаётся
  ничего — иначе на курсе появится отзыв от админа и лишний участник
  в счётчике. У заявки это ответ той же формы с `id: 0`: ни строки в базе,
  ни сообщения в бот;
- **доступ считается открытым**, даже если `enrollment` у админа нет, и
  **строгий порядок не запирает уроки**. В разделе 12 этого не написано, но
  без этого режим бесполезен: админ приходит из редактора урока 12 и с пустым
  прогрессом не откроет ничего, кроме первого;
- **попытка теста живёт в памяти сервиса** и выбрасывается при выходе. Она не
  переживает перезапуск бэкенда — режим ручной и одноразовый, это приемлемо.

Флаг живёт в сессии того приложения, где включён режим. Куки у приложений
разные, поэтому предпросмотр админа кабинет учителя в том же браузере
не задевает вовсе. Экран, показывающий курс, узнаёт о режиме из `GET /me`.

**Изменено в сессии 6:** у объекта пользователя появилось поле `preview` —
`null` вне режима, `{ "course_id": 1 }` внутри. Оно приходит везде, где
приходит пользователь: `GET /me` и `POST /auth/verify_code`.

```json
// GET /me в режиме предпросмотра — хвост объекта пользователя
{ "id": 3, "is_admin": true, "preview": { "course_id": 1 } }

// обычный вход
{ "id": 12, "is_admin": false, "preview": null }
```

Ошибки:

```json

// 403 forbidden — не админ
// 404 not_found — нет такой версии курса (enter)
```

# Сессия 7а — редакторы содержания

Экраны: `/courses` — список курсов, `/courses/{id}/edit` — редактор курса
с четырьмя вкладками, `/lessons/{id}`, `/quizzes/{id}`, `/tasks/{id}` в админке.

Всё в этом разделе требует админа. Порядок проверок один везде: вход (`401`),
права (`403 forbidden`), существование (`404`). Отдельного упоминания в каждом
эндпоинте ниже нет — сказано один раз здесь.

**Админ видит то, чего нет на площадке.** Черновики, скрытые версии, скрытые
уроки и скрытые вопросы приходят в эти ответы как обычные строки: фильтр
видимости каталога (`status IN planned|open|closed`) к админским спискам
не применяется вовсе. Это единственное место в контракте, где `GET` отдаёт
черновик, и единственное, где приходят правильные ответы теста.

## Правки курса, где уже учатся

Два запрета из `BACKEND_NOTES`, раздел 10. Оба — внятный ответ сервера
с числом, а не молчаливая ошибка при сохранении:

```json
// 409 has_progress — по уроку есть чей-то прогресс
{
  "error": {
    "code": "has_progress",
    "message": "Урок прошли 12 человек — его можно скрыть, но не удалить",
    "details": { "progress_count": 12 }
  }
}

// 409 has_attempts — вопрос уже показывали в попытках
{
  "error": {
    "code": "has_attempts",
    "message": "Вопрос был в 34 попытках — создайте новый, а этот скройте",
    "details": { "attempts_count": 34 }
  }
}
```

Из этого следуют два правила, которые действуют во всём разделе:

- **скрыть можно всегда.** `PATCH`, в котором нет ничего, кроме `is_hidden`,
  не отбивается никогда — иначе спрятать вопрос с попытками было бы нечем,
  а это ровно то, что предлагает текст ошибки;
- **«есть попытки» — это `question_order`, а не ответы.** Вопрос считается
  показанным, если он попал в состав хотя бы одной попытки, даже когда
  человек его пропустил: разбор всё равно покажет то, чего он не видел.

Скрыть можно всё три вида элемента: у урока `is_hidden` был с первой
миграции, у теста и задания появился в этой сессии. Правило одно на всех —
элемент с чужими данными не удаляется, а скрывается: на удаление приходит
`409 has_progress` у урока, `has_attempts` у теста и `has_submissions`
у задания, и дальше его прячут.

**Скрытый элемент исчезает у учителя целиком**, а не только из списка:
он не открывается по прямой ссылке, не попадает в программу и не считается
ни в прогрессе курса, ни в воронке отчёта — ни в числителе, ни в знаменателе.
В админском дереве программы он при этом виден с `is_hidden: true` — админ
должен видеть, что он спрятал.

**В условиях сертификата правило другое, и оно другое намеренно.** Скрытие
снимает требование, но не отбирает засчитанное:

- скрытый элемент перестаёт быть требованием для всех — скрыли несданный
  тест, и строка чек-листа считается без него;
- **но пройденное скрытие не отбирает**: элемент, который этот человек
  прошёл до того, как его спрятали, остаётся в его строке и числителем,
  и знаменателем. Иначе «1 из 1» превратилось бы в «0 из 0 — не начато»,
  и кнопка выдачи погасла бы у того, кто прошёл курс целиком;
- условие, под которым не осталось ни одного элемента, выполненным
  не считается — флаг, выставленный до наполнения курса, сертификатов
  не раздаёт.

Отсюда: строка чек-листа считается по видимым элементам плюс скрытым,
которые прошёл этот человек, а прогресс курса и проценты — по одним видимым.
Числа на двух экранах одного курса расходятся ровно в этом случае и ровно
по этой причине.

## Содержимое: `body` урока и `statement` задания

Форма, которую сессии 4 и 5 отложили сюда, зафиксирована:

```json
{ "html": "<h2>Дескриптор</h2><p>Наблюдаемое <b>действие</b>.</p>" }
```

Объект с единственным ключом `html`. Разметку **чистит сервер** по белому
списку из `DESIGN_BRIEF`, 5.18: `p`, `br`, `h2`, `h3`, `b`, `strong`, `i`,
`em`, `u`, `s`, `ul`, `ol`, `li`, `blockquote`, `a`, `table`, `thead`,
`tbody`, `tr`, `th`, `td`. Из атрибутов остаются `href` и `title` у `a`
(`href` — только `http`, `https`, `mailto`) и `colspan`/`rowspan` у ячеек;
`rel="noopener noreferrer"` сервер проставляет ссылкам сам, присылать его
не нужно. Всё остальное — теги, атрибуты, `style`, `on*`, `<script>` —
вырезается молча, без ошибки: редактор шлёт то, что получилось из вставки
из Word, и отбивать сохранение из-за лишнего `<span>` бессмысленно.

**Что вернулось из `PATCH`, то и лежит в базе.** Фронт после сохранения
показывает пришедший `html`, а не свой: иначе автор не увидит, что его
разметку почистили.

Пустой `html` — это пустое содержимое: у текстового урока `422`,
у видеоурока `body` можно прислать `null` и стереть заметку под видео.

## GET /admin/courses/{id}

**Изменено в сессии «Платформы 2»:** `price` заменён на `platforms` — см. «Редактор курса: публикация и цены».

Редактор курса целиком: четыре вкладки экрана живут этим одним ответом.
`404` — курса нет; черновик и скрытая версия здесь **не 404**, админ их правит.

`program` — то же дерево, что у `GET /courses/{id}/program`, с теми же
`kind` (`video | text | quiz | task`) и теми же полями по типу элемента, но
без `status` и **со скрытыми элементами**. Вместо статуса прохождения у каждого
элемента три админских признака:

- `is_hidden` — скрыт от учителей;
- `is_ready` — есть ли содержимое. Видеоурок готов, когда есть `video_url`;
  текстовый — когда `body.html` непустой; тест — когда есть хотя бы один
  видимый вопрос; задание — когда непустой `statement.html`. Это и есть бейдж
  «черновик / готов» в дереве;
- `has_data` — есть ли чужие данные: прогресс по уроку, попытки по тесту,
  сдачи по заданию. `true` — удаление отобьётся, меню показывает «Скрыть»
  вместо «Удалить», не дожидаясь ответа сервера.

`program_minutes` — сумма `time_required_min` по видимым элементам; это
и «всего по программе» внизу дерева, и серая подсказка у поля «Объём курса».

`readiness` — чек-лист вкладки «Публикация», считается от данных. `code` —
для ветвления, `text` — готовая строка по-русски, `items` — названия, которых
не хватает (пустой список, если перечислять нечего), `blocking` — держит ли
невыполненный пункт кнопку «Открыть набор».

Считается он **по видимым элементам**: скрытый — это черновик, которого учитель
не видит. Поэтому когда видимых элементов нет вовсе, пункты `empty_lessons`
и `empty_quizzes` говорят, что проверка не выполнялась, а не «нарушений нет»:
`ok` у них остаётся `true` (нарушений действительно нет), но `text` не выдаёт
пустоту за готовность. Пункт `program` в этом случае называет число скрытых —
иначе «нет ни одного элемента» при полном дереве на соседней вкладке читается
как потеря программы.

Флагов два, потому что на вкладке две кнопки и требования у них разные:

- `can_open` — «Открыть набор». Считается **только по пунктам с
  `blocking: true`**: они и есть то, без чего курс людям не показать.
  Неблокирующий пункт остаётся в чек-листе предупреждением и кнопку не держит.
  Сегодня такой пункт один — `cover`: курс без картинки в каталоге выглядит
  бедно, но пускать в него людей это не мешает. У всех остальных пунктов

- `can_plan` — «Опубликовать как запланированный». Условие одно — заполнена
  `starts_at`. **Запланированный курс публикуется и с пустыми уроками**
  (`DESIGN_BRIEF`, раздел 9): ради этого он и нужен — собирать заявки до того,
  как курс готов, а чек-лист показывает, что осталось доделать к старту.

Оба флага не зависят от нынешнего статуса курса: это ответ на вопрос «можно ли
нажать эту кнопку», а не «в каком состоянии курс сейчас».

`has_students` — есть ли хоть один действующий доступ. Экран по нему решает,

## PATCH /admin/courses/{id}

**Изменено в сессии «Платформы 2»:** `price` больше не принимается; публикация и цены приходят списком `platforms`, который заменяет набор целиком.

Меняет только присланные поля. Принимает всё, что редактирует вкладка
«Основное» и вкладка «Условия сертификата»: `title`, `short`, `full`, `cover`,
`category_id`, `hours`, `duration_text`, `price`, `status`, `starts_at`,
`strict_order` и четыре флага `cert_require_*`. Ответ — объект `GET`
целиком: чек-лист готовности и `program_minutes` пересчитываются, и экран
показывает их сразу.

`price: null` — «Цена по запросу». `starts_at` — дата без времени
(`"2026-09-01"`).

**`cover` принимает объект, а отдаёт строку.** На входе это загруженный файл —
`{ "key", "name" }` из ответа `POST /files`, как у картинок настроек, — либо
`null`, чтобы обложку снять:

```json
{ "cover": { "key": "uploads/2026/08/20/9f3c1a7e4b2d8c05.png", "name": "Обложка курса.png" } }
```

В ответе `cover` остаётся строкой-адресом, и форма его нигде не менялась:
сервер сам собирает публичный адрес раздачи `GET /courses/{id}/cover`
(см. ниже). Ключ объекта наружу не уходит — как и у картинок настроек.
**Строкой-адресом обложка больше не задаётся:** прежнее
`{"cover": "https://…"}` отвечает `422`.

Файл проверяется на то, что объект в хранилище есть и что это картинка,
причём по байтам объекта, а не по имени: PNG, JPEG, GIF, WEBP или SVG.
Пропорции и размер в пикселях сервер не проверяет: «16:9, минимум 640×360»
из брифа — подсказка человеку на экране.

**Старые обложки-ссылки продолжают читаться.** У курсов, заведённых до
загрузки файлом, в базе лежит внешний адрес, вписанный руками; пока
загруженной картинки нет, он и уходит в `cover` как есть. Это переходное
поведение на время, а не вторая равноправная возможность: задать такой адрес
через API уже нельзя, и первая же загрузка файлом его гасит. `"cover": null`
снимает и загруженную картинку, и старый адрес.

**Публикация — это тот же `PATCH` со сменой `status`,** отдельной ручки нет:
три кнопки вкладки «Публикация» шлют `draft`, `planned` и `open`. Смена
статуса на публичный (`planned | open | closed`) проверяет минимум, без
которого курс нельзя показывать людям: непустое `title`, `hours` от 1,
`category_id` из справочника. У `planned` сверх этого обязательна `starts_at` —
именно она рисует бейдж «Старт 1 сентября». Наполненность программы
не проверяется нигде: запланированный курс для того и публикуют пустым.

Проходного балла у курса нет и не появится: он свой у каждого теста
(`quiz.pass_score`), и вкладка «Условия» его не редактирует — иначе экран
результата теста и чек-лист сертификата показали бы разные числа.

Ошибки:

```json

{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "starts_at", "message": "У запланированного курса дата старта обязательна" } ] }
  }
}

// 422 validation_error — обложкой прислали не картинку
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "cover", "message": "Нужна картинка: PNG, JPEG, GIF, WEBP или SVG" } ] }
  }
}

// 404 not_found — ключа обложки нет в хранилище
{ "error": { "code": "not_found", "message": "Загруженный файл не найден — загрузите его заново" } }
```

## GET /courses/{id}/cover

**Публичный, без входа.** Отдаёт **байты** обложки курса: каталог открывают
все, и картинка в нём обязана рисоваться без куки. Тот же адрес показывает
превью в редакторе, поэтому статус курса раздачу не запирает — черновик
отдаёт обложку так же, как открытый курс.

Адрес собирает сервер сам и кладёт его в поле `cover` каждого ответа, где
курс есть: каталог, страница курса, «мои курсы», список курсов админки
и редактор. Ключ объекта наружу не уходит.

Отдельным путём, а не подписанной ссылкой, по той же причине, что
и `GET /branding/{slot}`: обложка стоит на странице, которую открывают без
входа, и ссылка со сроком жизни там протухала бы на каждом заходе.
Хранилище при этом остаётся приватным — публичного бакета нет нигде
(`BACKEND_NOTES`, раздел 9).

Ответ кэшируется на 5 минут — меньше, чем логотип: адрес обложки у курса
один и тот же, а заменивший картинку админ смотрит на результат тут же,
в редакторе.

`404` — и когда курса нет, и когда обложку не загружали, и когда объект
из хранилища пропал: для открывшего адрес это одно и то же.

```json
// 404 not_found
{ "error": { "code": "not_found", "message": "Обложка не найдена" } }
```

## DELETE /admin/courses/{id}

`204`. Удаляется вместе со всей программой — модулями, уроками, тестами,
вопросами, вариантами, заданиями и материалами.

Курс, которого кто-то коснулся, не удаляется совсем: доступ, заявка или
строка сертификата — каждый из них останавливает удаление. Считается всё,
включая отозванные доступы, закрытые заявки, а у сертификата — **и заявку,
и отозванный документ**: строка в отчёте, ссылающаяся на несуществующий курс,
дороже лишней кнопки.

```json
// 409 course_in_use — курс уже кому-то выдавали
{
  "error": {
    "code": "course_in_use",
    "message": "Курс нельзя удалить: 12 доступов, 3 заявки, 4 сертификата",
    "details": { "enrollments": 12, "leads": 3, "certificates": 4 }
  }
}
```

## POST /admin/courses/{id}/versions

**Изменено в сессии «Платформы 2»:** новая языковая версия заводится без единой площадки, цены у неё нет вовсе.

Кнопка «Создать казахскую версию» в шапке редактора. Заводит **новый курс
с тем же `group_id`** и другим языком: русская и казахская версии — два
самостоятельных курса, совпадать один в один они не обязаны
(`BACKEND_NOTES`, раздел 3).

`copy_program: true` — чекбокс «Скопировать структуру программы как
заготовку». Копируется структура и содержимое: модули, уроки со всем текстом
и ссылками, тесты с настройками, вопросами и вариантами, задания с условием.
Не копируется ничего чужого — ни доступов, ни прогресса, ни материалов
уроков: файл лежит в хранилище один, и две строки на один ключ означают,
что удаление из одной версии ломает вторую.

Новая версия всегда черновик, цена и дата старта у неё свои и пустые:
цену на казахскую версию ставят отдельно, и молча продублировать её нельзя.

Ответ — объект `GET /admin/courses/{id}` **новой** версии.

```json
// запрос
{ "lang": "kz", "copy_program": true }
```

Ошибки:

```json
// 409 version_exists — версия на этом языке в группе уже есть
{
  "error": {
    "code": "version_exists",
    "message": "Қазақша нұсқа у этого курса уже есть",
    "details": { "course_id": 2 }
  }
}

// 422 validation_error — lang совпадает с языком исходного курса
```

## POST /admin/courses/{id}/duplicate

**Изменено в сессии «Платформы 2»:** дубликат заводится без единой площадки.

Пункт «Дублировать» в меню списка курсов. В отличие от языковой версии,
делает **новую группу**: это другой курс, а не второй язык этого.

Копируется всё содержимое и программа, заголовок получает пометку «(копия)»,
статус — черновик, `starts_at` и `price` пустые. Материалы уроков и файлы-шаблоны
не копируются по той же причине, что и в языковой версии.

Ответ — объект `GET /admin/courses/{id}` копии.

Переименование. Единственное поле — `title`. Ответ — модуль с элементами.

## DELETE /admin/modules/{id}

`204`. Удаляется вместе со своими уроками, тестами и заданиями — модуль
без содержимого никому не нужен, а вычищать его поэлементно перед удалением
значит десять раз спросить одно и то же.

Останавливает удаление ровно то же, что и поштучно: чужие данные внутри.
Хоть один урок с прогрессом, тест с попытками или задание со сдачами —
`409`, и в `details` сказано, что именно держит.

```json

{
  "error": {
    "code": "module_in_use",
    "message": "В модуле есть элементы с чужими данными — сначала разберитесь с ними",
    "details": {
      "items": [
        { "kind": "video", "id": 1, "title": "Что не так с пятибалльной шкалой", "reason": "has_progress" },
        { "kind": "quiz", "id": 1, "title": "Тест модуля 1", "reason": "has_attempts" }
      ]
    }
  }

```

## POST /admin/modules/{id}/lessons, /quizzes, /tasks

Три кнопки окна «Добавить в программу». Все три создают **заготовку**:
название, требуемое время и то минимальное, без чего строка в базе не
существует. Наполняют её потом, в своём редакторе — поэтому ответ каждого
из трёх это объект соответствующего редактора целиком
(`GET /admin/lessons/{id}` и далее), а фронт сразу уводит на него.

Элемент встаёт последним в модуле. Заготовка всегда не `is_ready`, и это
нормально: дерево покажет её как «черновик».

```json
// POST /admin/modules/1/lessons — вид урока выбран переключателем в окне
{ "title": "Обратная связь без оценки", "kind": "video", "time_required_min": 15 }

// POST /admin/modules/1/quizzes
{ "title": "Тест модуля 5", "time_required_min": 15, "is_final": false, "pass_score": 70 }

// POST /admin/modules/1/tasks
{ "title": "Опишите свой опыт", "time_required_min": 40 }
```

Заготовка урока обходит проверку «у видеоурока обязателен `video_url`»:
в момент создания ссылки ещё нет, она появится в редакторе. Это единственное
место, где урок сохраняется пустым.

**Заготовка заводится скрытой** — все три отвечают `is_hidden: true`. Курс
правят и тогда, когда в нём уже учатся, а пустая заготовка в открытом курсе
видна учителю в ту же секунду: пустой видеоурок открывается и не проигрывается,
а пустой тест входит в условия сертификата и отдаёт `409 quiz_empty` на попытку —
то есть документ по курсу перестаёт получать кто бы то ни было. Показывают
заготовку, когда она наполнена: `is_hidden: false` в `PATCH` своего редактора.

Чек-лист готовности курса считает по видимым элементам, поэтому скрытая
заготовка не попадает ни в `empty_lessons`, ни в `empty_quizzes` и `can_open`
не гасит. Потеряться ей негде: в дереве редактора она на месте и помечена
сразу и «черновиком» (`is_ready: false`), и «скрыт» (`is_hidden: true`).

Ошибки:

```json
// 422 validation_error — пустое название, time_required_min вне 0..600,
// pass_score вне 1..100
```

## PUT /admin/courses/{id}/program_order

Перетаскивание в дереве программы. Приходит **всё дерево целиком**, а не
переставленная пара: сервер расставляет `order_index` по позициям в массивах
и заодно переносит элемент в другой модуль, если он оказался в чужом `items`.

`kind` — тот же, что в ответах: `video` и `text` оба означают урок, но
приходят как есть, чтобы фронт слал обратно то, что получил.

**Неполное дерево отбивается.** Если в теле не хватает хотя бы одного модуля
или элемента курса — или встретился лишний, чужой — приходит `422` и не
меняется ничего. Правило простое: пока экран не знал о новом уроке, его
перетаскивание не должно этот урок потерять.

Ответ — `program` и `program_minutes` в той же форме, что в редакторе курса:
экран перерисовывает дерево ответом сервера, а не своим оптимистичным.

```json
// запрос
{
  "modules": [
    { "id": 1, "items": [ { "kind": "text", "id": 2 }, { "kind": "video", "id": 1 } ] },
    { "id": 2, "items": [ { "kind": "quiz", "id": 2 }, { "kind": "task", "id": 1 } ] }
  ]
}

// 200
{ "program": [ { "id": 1, "title": "Модуль 1…", "items": [] } ], "program_minutes": 260 }
```

Ошибки:

```json
// 422 validation_error — дерево неполное или в нём чужой элемент
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": {
      "fields": [ { "field": "modules", "message": "В дереве не хватает элементов курса: 2" } ]
    }
  }
}
```

## GET /admin/lessons/{id}

Редактор урока. От учительского `GET /lessons/{id}` отличается тремя вещами,
и все три намеренные:

- **`video_url` приходит.** Учителю ссылку не отдают никогда — только
  подписанный `playback`, — но админ её редактирует, и без неё поле пустое;
- приходит скрытый урок и урок невидимого курса;
- вместо `is_completed` — админские `is_hidden`, `is_ready`, `has_data`.

`course` и `module` — хлебные крошки шапки редактора; `course.lang` рисует
метку языка, переключателя языка в уроке нет.

`files` — материалы по `order_index`, с `id` строки. Ключа хранилища здесь
нет, как и везде: он уходит наружу только тому, кто прямо сейчас загрузил
файл (`POST /files`).

`video_url` приходит **как он лежит в базе**. `PATCH` приводит ссылку
к одному написанию, но строки, заведённые до этой сессии, так и останутся
в том виде, в каком их сохранили, — поэтому в примере ниже короткая
`youtu.be`, а не нормализованная форма.

```json
{
  "id": 1,
  "module_id": 1,
  "course": { "id": 1, "lang": "ru", "title": "Критериальное оценивание в начальной школе" },
  "module": { "id": 1, "title": "Модуль 1. Зачем менять оценивание" },
  "title": "Что не так с пятибалльной шкалой",
  "kind": "video",
  "body": { "html": "<p>Короткая заметка к видео.</p>" },
  "video_url": "https://youtu.be/dQw4w9WgXcQ",
  "duration_label": "14:20",
  "time_required_min": 20,
  "is_hidden": false,
  "is_ready": true,
  "has_data": true,
  "files": [
    { "id": 1, "name": "Памятка по критериям.pdf", "size_bytes": 184320, "mime": "application/pdf" }
  ]
}

// заготовка, только что созданная из дерева программы
{
  "id": 12,
  "module_id": 1,
  "course": { "id": 1, "lang": "ru", "title": "Критериальное оценивание в начальной школе" },
  "module": { "id": 1, "title": "Модуль 1. Зачем менять оценивание" },
  "title": "Обратная связь без оценки",
  "kind": "video",
  "body": null,
  "video_url": null,
  "duration_label": null,
  "time_required_min": 15,
  "is_hidden": false,
  "is_ready": false,
  "has_data": false,
  "files": []
}
```

## PATCH /admin/lessons/{id}

Поля: `title`, `kind`, `body`, `video_url`, `duration_label`,
`time_required_min`, `is_hidden`. Ответ — объект `GET` целиком.

**Проверяется то, что получится, а не то, что было.** Присланный `kind`
складывается с присланным содержимым, и уже эта пара проверяется на правило
из `BACKEND_NOTES`, раздел 2: у видеоурока обязателен `video_url`,
у текстового — непустой `body.html`. Поэтому смена вида урока одним запросом
вместе с новым содержимым проходит, а смена вида в одиночку — отбивается
`422` с полем, которое осталось незаполненным.

`video_url` — только YouTube, других хостингов пока нет
(`DESIGN_BRIEF`, 5.18). Принимаются все обычные написания ссылки
(`youtu.be/…`, `watch?v=…`, `embed/…`, `shorts/…`, `live/…`), и сохраняется
**нормализованный** вид `https://www.youtube.com/watch?v=<id>`: иначе одно
и то же видео лежит в базе четырьмя разными строками.

Длительность вводится руками: по чужой ссылке она ненадёжна.

**Пустое сохранение не проходит молча** — это прямое требование экрана.
Текст ошибки берётся с него же.

Ошибки:

```json
// 422 validation_error — видеоурок без ссылки
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "video_url", "message": "Без ссылки видеоурок не сохранится" } ] }
  }
}

// 422 validation_error — ссылка не похожа на YouTube
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "video_url", "message": "Не похоже на ссылку YouTube — проверьте адрес" } ] }
  }
}

// 422 validation_error — текстовый урок без текста
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "body", "message": "Без текста текстовый урок не сохранится" } ] }
  }
}
```

## DELETE /admin/lessons/{id}

`204`. Вместе с уроком уходят его материалы и вопросы учителей под ним:
вопрос к несуществующему уроку в очередь админа всё равно не попадёт —
она собирается джойном по уроку.

Урок, который кто-то прошёл, не удаляется — `409 has_progress`, и дальше
его прячут: `PATCH { "is_hidden": true }`. Причина в `BACKEND_NOTES`,
раздел 10: у сорока человек «12 из 18» превратится в «12 из 17», а у кого-то
условия сертификата выполнятся сами собой.

## POST /admin/lessons/{id}/files

Привязывает уже загруженный файл к уроку. Тело — `key` из ответа
`POST /files` и имя, которое увидит учитель. Размер и `mime` сервер берёт
сам: размер — из хранилища, `mime` — из имени, а не из того, что прислал
браузер.

Файл встаёт последним. Ответ — созданная строка в той же форме, что
в `files[]` редактора.

```json
// запрос
{ "key": "uploads/2026/08/18/9f3c1a7e4b2d8c05.pdf", "name": "Памятка по критериям.pdf" }

// 200
{ "id": 5, "name": "Памятка по критериям.pdf", "size_bytes": 184320, "mime": "application/pdf" }
```

Ошибки:

```json
// 404 not_found — в хранилище нет объекта с таким ключом
{ "error": { "code": "not_found", "message": "Загруженный файл не найден — загрузите его заново" } }
```

## DELETE /admin/lesson_files/{id}

`204`. Отвязывает материал от урока. Байты в приватном хранилище остаются:
порт `storage` умеет писать, читать и мерить, но не удалять, и заводить
удаление ради этой кнопки сессия не стала. Уборка хранилища — отдельная
задача.

## GET /admin/quizzes/{id}

Редактор теста: настройки сверху и список вопросов. **Здесь приходят
правильные ответы** — `is_correct` у каждого варианта и `explanation`
у вопроса. Учительский `GET /quizzes/{id}` не отдаёт ни того, ни другого,
и это единственный эндпоинт во всём контракте, где верные ответы уходят
наружу. Права проверяются на сервере, а не тем, что экран лежит на другом
домене.

ли **этот** вопрос в состав хотя бы одной попытки. Второе и запрещает правку:
экран по нему показывает замок, не дожидаясь `409`.

## PATCH /admin/quizzes/{id}

Настройки теста: `title`, `is_final`, `pass_score`, `time_limit_min`,
`shuffle`, `show_review`, `retakable`, `time_required_min`, `is_hidden`.
Ответ — объект `GET` целиком.

`time_limit_min: null` — таймера нет; переключатель «Таймер» на экране
и есть выбор между `null` и числом.

Настройки правятся и у теста с попытками — запрет из раздела 10 касается
**вопросов**, а не правил. Что при этом не меняется задним числом: `passed`
и `score` уже завершённых попыток посчитаны на старом проходном балле
и такими и остаются. Иначе поднятие проходного отобрало бы у людей уже
полученный зачёт, а вместе с ним и выданный сертификат.

**Итоговый тест в курсе один.** Попытка сделать вторым итоговым ещё один
тест отбивается: отчёт по курсу считает средний балл по итоговому и берёт
первый попавшийся, а чек-лист сертификата пишет «Сдать итоговый тест»
в единственном числе.

Ошибки:

```json
// 409 final_quiz_exists — в курсе уже есть итоговый тест
{
  "error": {
    "code": "final_quiz_exists",
    "message": "Итоговый тест в курсе уже есть: «Итоговый тест»",
    "details": { "quiz_id": 2 }
  }
}

// 422 validation_error — pass_score вне 1..100, time_limit_min вне 1..600
```

`204`. Удаляется с вопросами и вариантами.

Тест, который кто-то проходил, не удаляется: `409 has_attempts`. Дальше
его прячут — `PATCH { "is_hidden": true }`, как урок с прогрессом.

## POST /admin/quizzes/{id}/questions

Вопрос вместе с вариантами, одним телом: варианта без вопроса не бывает,
и заводить их двумя запросами значит оставлять в базе вопросы без ответов,
когда второй запрос не дошёл.

Вопрос встаёт последним. Ответ — созданный вопрос в форме элемента
`questions[]`.

Правила зачёта, которые проверяет сервер:

- вариантов от 2 до 10;
- `single` — ровно один правильный;
- `multi` — правильных хотя бы один, и вариантов хотя бы три: «несколько
  правильных» из двух вариантов это `single` наоборот;
- `bool` — ровно два варианта и ровно один правильный;
- частичных баллов нет: в `multi` зачёт только за полностью верный набор.
  Это правило домена, оно уже действует в сессии 5, и редактор его не меняет —
  но подпись под вариантами на экране про него говорит.

Дублирование вопроса отдельной ручкой не делается: у экрана уже есть весь
вопрос целиком, и «дублировать» — это тот же `POST` с тем же телом.

```json
// запрос
{
  "type": "single",
  "text": "Что описывает дескриптор?",
  "explanation": "Дескриптор — про наблюдаемое действие.",
  "points": 1,
  "options": [
    { "text": "Наблюдаемое действие ученика", "is_correct": true },
    { "text": "Отношение ученика к предмету", "is_correct": false }
  ]
}
```

Ошибки:

```json
// 422 validation_error — в single не один правильный ответ
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "options", "message": "В вопросе с одним ответом правильный ровно один" } ] }
  }
}
```

## PATCH /admin/quiz_questions/{id}

Путь не `/admin/questions/{id}`: там уже живёт очередь вопросов учителей
под уроками (сессия 6), и два разных «вопроса» в одном пространстве имён
рано или поздно сойдутся не тем эндпоинтом.

Поля: `type`, `text`, `explanation`, `points`, `is_hidden` и `options`
целиком — варианты присылаются полным списком и заменяют прежние. Частичной
правки одного варианта нет: у вопроса их два-три, а отдельные ручки на
вариант — это ещё три эндпоинта ради экономии килобайта.

**Вопрос с попытками не редактируется.** Любое поле, кроме `is_hidden`,
отбивается `409 has_attempts`; текст ошибки предлагает то, что и должен:
создать новый вопрос, а этот скрыть. Запрос, в котором нет ничего, кроме
`is_hidden`, проходит всегда — иначе выполнить этот совет было бы нечем.

Ответ — обновлённый вопрос.

## DELETE /admin/quiz_questions/{id}

`204`, варианты уходят вместе с ним. Вопрос с попытками не удаляется —
`409 has_attempts`, дальше `PATCH { "is_hidden": true }`.

## GET /admin/tasks/{id}

Редактор задания. От учительского `GET /tasks/{id}` отличается тем же, чем
редактор урока: приходит задание невидимого курса, вместо истории сдач —
админские признаки, а `template_file` показан так же, как учителю, — именем,
размером и типом, без ключа хранилища.

```json
{
  "id": 1,
  "module_id": 1,
  "course": { "id": 1, "lang": "ru", "title": "Критериальное оценивание в начальной школе" },
  "module": { "id": 1, "title": "Модуль 1. Зачем менять оценивание" },
  "title": "Составьте дескрипторы к своему уроку",
  "statement": { "html": "<p>Возьмите ближайший урок и составьте…</p>" },
  "template_file": { "name": "Шаблон дескрипторов.docx", "size_bytes": 25600, "mime": "application/vnd.openxmlformats-officedocument.wordprocessingml.document" },
  "submit_format": "both",
  "allowed_ext": ["pdf", "doc", "docx"],
  "max_size_mb": 20,
  "time_required_min": 40,
  "is_hidden": false,
  "is_ready": true,
  "has_data": true
```

## PATCH /admin/tasks/{id}

Поля: `title`, `statement`, `submit_format`, `allowed_ext`, `max_size_mb`,
`time_required_min`, `is_hidden` и `template_file` — последний принимает `key`
из `POST /files` либо `null`, чтобы шаблон убрать.

`allowed_ext` — расширения без точки и в нижнем регистре (`["pdf", "docx"]`),
как их проверяет сдача работы в сессии 5. Экран показывает их группами
(«JPG / PNG»), но на границу уходит список расширений, а не подписи.
Пустой список — ограничения нет.

`max_size_mb` — от 1 до 20: потолок в 20 стоит у загрузки (`POST /files`),
и задание не может обещать больше, чем примет сервер.

Типов заданий нет: вид задания — это методика, а не настройка
(`DESIGN_BRIEF`, 5.20). Оценка тоже не настраивается — только зачтено или
на доработку, без баллов.

```json
// запрос — шаблон заменяется, формат сдачи сужается до файла
{
  "statement": { "html": "<p>Возьмите ближайший урок…</p>" },
  "submit_format": "file",
  "allowed_ext": ["pdf", "docx"],
  "template_file": { "key": "uploads/2026/08/19/3a1f…", "name": "Шаблон.docx" }
}
```

Ошибки:

```json
// 422 validation_error — max_size_mb больше потолка загрузки
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "max_size_mb", "message": "Больше 20 МБ сервер не примет" } ] }
  }
}
```

## DELETE /admin/tasks/{id}

`204`. Задание со сдачами не удаляется — `409 has_submissions`; дальше
его прячут — `PATCH { "is_hidden": true }`.

# Сессия 7б — люди и площадка

Экраны: `/teachers` и карточка учителя, `/reviews`, `/settings` в админке;
кнопка «Скачать PDF» на `/certificates/{id}` в клиентском приложении.

Всё, что под `/admin`, требует админа: порядок проверок тот же — вход (`401`),
права (`403`), существование (`404`).

**Здесь живут персональные данные.** ФИО, телефоны, школы и регионы учителей —
причина, по которой админка вынесена на отдельный домен. Из этого следует
для эндпоинтов ниже: они отдают персональные данные **только админу и только
по проверке на сервере**; ни одно из этих полей не попадает в логи, в тексты
ошибок и в публичные ответы. Публичного эндпоинта, отдающего список учителей,
в контракте нет и не будет.

## GET /admin/teachers

Список учителей. Пагинация стандартная, свежие сверху. Фильтры: `region`,
`school`, `course_id` (учителя с действующим доступом к этой версии курса),

## GET /admin/teachers/{id}

Карточка: профиль слева, четыре вкладки справа. Всё одним ответом — у одного
человека курсов, тестов, работ и сертификатов заведомо немного, и пагинации
экран не рисует.

`courses` — по строке на доступ, включая отозванные (`revoked_at`): прогресс
и результаты при закрытии доступа не удаляются, и админ должен их видеть.
`paid_note` — комментарий выдачи («сумма, способ, дата — для истории»).

**`progress_percent` считается не по урокам, а по всей программе** — тестам
и заданиям тоже, той же формулой, что в кабинете учителя и в отчёте по курсу.

подписи «12 из 18». Считать процент из этой пары на фронте нельзя: одно и то же
число, разошедшееся на двух экранах, читается как ошибка.

не показывал живую кнопку, которая ответит `409`.

## PATCH /admin/teachers/{id}

Карточка учителя правится админом целиком: блокировка, номер телефона
и **весь профиль**. Опечатку в ФИО или в ИИН чинить больше некому — учитель
свой ИИН только видит, а в реестр академии строка уходит как есть
(открытый вопрос 1 из `SESSION_C3_QA`, закрыт 06.09.2026).

Поля, все необязательные: `is_blocked`, `phone`, `first_name`, `last_name`,
`middle_name`, `iin`, `email`, `school`, `position`, `region`, `city`,
`subject`, `experience`.

Трёх полей здесь нет нарочно, и неизвестное поле — 422 (`extra: forbid`):

- `lang` — личная настройка интерфейса человека, а не запись о нём: админ,
  тронув её, молча переключил бы учителю язык кабинета;
- `is_admin` — права выдаются на своей странице настроек, снятия прав
  в продукте нет;
- `photo_url` — загрузки фото не существует.

Правила полей профиля — те же, что у `PATCH /me`, буква в букву (это один
и тот же сценарий, а не вторая его копия): строки чистятся от краевых пробелов,
`null` у строки — «стереть», `experience` — число лет от 0 до 70 или `null`.
У `iin` `null` — «не трогать»: снять ИИН нельзя, иначе админ упрётся в пустое
поле тогда, когда учитель уже всё сдал и ждёт документ.

Ответ — **карточка целиком**, той же формы, что у `GET /admin/teachers/{id}`:
экран перерисовывает её ответом.

`null` стирает строку, пробелы по краям снимаются:

```json
{ "id": 6, "school": "", "city": "Астана" }
```

**ФИО в уже выданных сертификатах правка профиля не меняет.** `holder_name` —
снимок момента заявки, и живёт он в строке документа; правится он на карточке
сертификата, `PATCH /admin/certificates/{id}`. Исправив фамилию здесь, админ
чинит человека, а не выданные ему бумаги: документы задним числом
не переписываются. Если фамилию нужно исправить и на документе — это второй
запрос, к сертификату.

**ИИН на бумаге, наоборот, читается из живой таблицы.** Колонки `iin`
у сертификата нет (`CERTIFICATES_BRIEF`, 5), и лист берёт номер у владельца
в момент печати — значит, исправленный ИИН попадёт в PDF, скачанный после
правки. Это и есть способ починить опечатку в номере на уже выданном
документе.

**Блокировка действует сразу**, не дожидаясь конца сессии: следующий запрос
заблокированного вернёт `403 blocked`. Профиль, прогресс и документы остаются
на месте — блокировка это запрет входить, а не удаление человека.

**Смена номера — это восстановление доступа**, а не правка справочной строки:
вход только по SMS, и человек, сменивший симку, теряет аккаунт вместе
с сертификатами (`DESIGN_BRIEF`, 9). Номер нормализуется к `+7XXXXXXXXXX`,
как при входе. Все сессии этого человека **отзываются**: старый телефон
у него уже не в руках, и живая сессия на нём — чужая. Присланный тот же самый
номер сессий не трогает — менять нечего.

Себя админ заблокировать не может: иначе платформа остаётся без администратора,
а починить это будет некому.

Запрос — одна транзакция: отказ по любому полю не оставляет наполовину
применённую правку. Отправленные вместе фамилия и чужой ИИН не сохранят
ни того, ни другого.

Ошибки:

```json
// 409 iin_taken — номер уже стоит в чужом аккаунте
{
  "error": {
    "code": "iin_taken",
    "message": "Этот ИИН уже указан в другом аккаунте"
  }
}
```

**`details` у `iin_taken` пустые нарочно** (решение владельца 04.09.2026),
и этим отказ отличается от `phone_taken`, который отдаёт `user_id`: номер
телефона админ меняет, чиня доступ конкретному человеку, а в ИИН упирается
кто угодно, и назвать аккаунт значит отдать его тому, кто перебирает чужие
номера. Ни телефона, ни ФИО владельца номера в ответе тоже нет. Свой же ИИН
занятым не считается — повторное сохранение карточки проходит.

## POST /admin/teachers/{id}/retakes

«Разрешить пересдачу» — кнопка, без которой одна попытка означает потерю курса
насовсем: пропал интернет, разрядился телефон, вкладку закрыл ребёнок
(`DESIGN_BRIEF`, 5.22). Тело: `quiz_id` и **обязательная** `reason` — она
остаётся в истории попытки, и по ней потом разбирают, почему зачёт снят.

Как это устроено: зачётная попытка перестаёт быть зачётной. Строка никуда
не девается — на вкладке «Тесты» видны все попытки с датами и баллами, и у снятой
показаны причина и время. Освобождается частичный уникальный индекс
`uq_quiz_attempt_counted`, и следующая попытка человека снова становится
зачётной. Никакие ответы и баллы прошлой попытки не переписываются.

Ответ — карточка учителя целиком: экран перерисовывает вкладку «Тесты» ответом.

```json
// запрос
{ "quiz_id": 1, "reason": "Пропал интернет на 12-й минуте, попытка сгорела." }
```

Ошибки:

```json
// 409 quiz_retakable — у пересдаваемого теста разрешать нечего
{ "error": { "code": "quiz_retakable", "message": "Тест и так пересдаваемый — попыток не ограничено" } }

// 409 no_attempt — зачётной попытки нет, пересдавать нечего
{ "error": { "code": "no_attempt", "message": "Человек ещё не проходил этот тест" } }

// 409 attempt_in_progress — попытка идёт прямо сейчас
{ "error": { "code": "attempt_in_progress", "message": "Попытка ещё не завершена — дождитесь её конца" } }

// 409 certificate_issued — по курсу есть действующая строка сертификата.
// Код один на оба случая, текст разный — экран показывает текст сервера
{ "error": { "code": "certificate_issued", "message": "Сертификат по курсу уже выдан — пересдача закрыта" } }

// он же, когда документ пока только попросили
{ "error": { "code": "certificate_issued", "message": "Заявка на сертификат отправлена — пересдача закрыта" } }

// 422 validation_error — пустая причина
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "reason", "message": "Причина обязательна — она остаётся в истории" } ] }
  }
}
```

Учителю уходит уведомление `retake_allowed` с `course_id`, `quiz_id`
и `quiz_title`: иначе он не узнает, что тест снова открыт, и будет считать
курс потерянным.

## DELETE /admin/enrollments/{id}

«Закрыть доступ». `204`. Проставляет `revoked_at`; прогресс, попытки, сдачи
и выданные сертификаты **не удаляются** — экран так и обещает. Строка доступа
остаётся в карточке учителя с отметкой об отзыве.

Повторный вызов на уже отозванном — `204` и ничего не меняет: `revoked_at`
остаётся временем первого отзыва.

Открывают доступ обратно тем же `POST /admin/enrollments`, что и в первый раз
(сессия 3): он снимает `revoked_at` у существующей строки.

## POST /admin/reviews/{id}/reply

Ответ администратора на отзыв. Повторный вызов **меняет** ответ — на экране
это кнопка «Изменить ответ», отдельной ручки правки нет. Ответ виден всем
на странице курса.

**Закрывает вопрос сессии 3:** там у отзыва в публичном ответе стояло
`"reply": null` с пометкой «ответу админа негде храниться». Теперь есть где —
ответ лежит у самого отзыва, а не отдельным сообщением треда: ответ у отзыва
один, и вторых уровней у него не бывает.

**Изменено в сессии 7б:** `GET /courses/{id}/reviews` отдаёт в `reply` объект
`{ "text", "created_at" }` вместо всегдашнего `null`. Имени отвечающего там
нет — на экране он подписан просто «Администратор».

```json
// запрос
```

`204`. Убирает отзыв из ленты админа и со страницы курса, и снимает его

`204`. Админ может удалить любое сообщение под уроком — и вопрос, и ответ

`GET /admin/questions`, и не считается в счётчиках дашборда.

## PATCH /admin/settings

**Изменено в сессии «Платформы 2»:** принимается только `telegram`, любое поле бренда — `422`.

Меняет только присланное. Поля: `platform_name`, `org_name`, `contacts`,
`logo` и `certificate_images.*` — каждая картинка принимает
`{ "key", "name" }` из ответа `POST /files` либо `null`, чтобы её убрать.
Флаги `telegram.notify_leads`, `telegram.notify_submissions`
и `telegram.notify_certificates` — тоже здесь; привязка бота меняется своими
ручками ниже, а не этим `PATCH`.

**`contacts` сливается по полям, а не заменяется объектом целиком.**
Присланные поля перезаписываются, неприсланные остаются как были. Частичная
отправка легальна и ничего не стирает: `{"contacts": {"phone": "+7…"}}`
меняет телефон и оставляет нетронутыми `name`, `whatsapp`, `telegram`
и `hours`. Чтобы очистить поле, его надо прислать пустой строкой.

**`null` в теле значит две разные вещи — смотря в каком поле:**

- у `logo` и у `certificate_images.*` `null` **снимает картинку**;
- у `platform_name`, `org_name` и у любого поля внутри `contacts` `null`
  значит «поле не прислали» — оно остаётся как было. Стирает такое поле
  **пустая строка**.

Отсюда предупреждение фронту: привычное «пустой инпут → `null`» на текстовых
полях даст `200` и прежнее значение в ответе — сохранения не произойдёт,
и человек увидит это только после перезагрузки экрана. Очищенное поле формы
надо слать пустой строкой.

Ответ — объект `GET` целиком.

Картинки проверяются на то, что объект в хранилище есть и что это картинка,
причём по байтам объекта, а не по имени файла. Допустимые форматы зависят
от слота: `logo` берёт любую картинку, включая `svg` — он стоит на лендинге;
три слота `certificate_images.*` принимают **только `image/png`
и `image/jpeg`**, потому что шаблон сертификата рисует fpdf2, `svg` он
не возьмёт, и место под печатью на выданном документе останется пустым.
Текст ошибки у слотов разный — каждый называет то, что берёт он сам.

Ошибки:

```json
// 404 not_found — ключа нет в хранилище
{ "error": { "code": "not_found", "message": "Загруженный файл не найден — загрузите его заново" } }

// 422 validation_error — файл не картинка или формат не для сертификата
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "certificate_images.stamp", "message": "Нужна картинка: PNG или JPEG" } ] }
  }
}
```

Добавить администратора. Тело — один `phone`, ответ — добавленная строка

по SMS: `phone` в базе уникален, и первый вход этого человека не создаст
второго. Знакомому номеру — учителю — права выдаются, профиль остаётся.

Снятия прав нет: админов заводят редко и всерьёз, а кнопка, которой можно
снять права себе или последнему админу, стоит дороже похода в базу в тот
редкий раз, когда это правда нужно (владелец, 21.08.2026).

```json
// 422 validation_error — номер не казахстанский, уже админ или заблокирован
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [{ "field": "phone", "message": "Этот номер уже администратор" }] }
  }
}
```

**Админ в показателях — призрак.** Доступ к курсу админу выдают той же
кнопкой, что и учителю, и курс он проходит как все. Но ни в одно число он
не входит: его нет в списке учителей и в счётчике дашборда, и с 21.08.2026
нет ни в сводке отчёта (`granted`, `started`, `completed`, средние,
`certificates`), ни в воронке, ни в таблице участников. Иначе отчёт по курсу
и список учителей показывали бы разное число людей.

## Telegram-бот: привязка

Бот — единственный способ, которым админ узнаёт о новых заявках и работах
на проверку: колокольчика в админке нет (`BACKEND_NOTES`, раздел 11).

**`chat_id` нельзя вписать руками** — и это не придирка к интерфейсу:
чужой `chat_id`, вписанный по ошибке, отправляет заявки с телефонами учителей
незнакомому человеку. Поэтому привязка идёт от бота: админ жмёт «Подключить»,
получает код, отправляет боту `/start <код>`, и `chat_id` записывает сервер,
приняв сообщение.

### POST /admin/settings/telegram/bind_code

Выдаёт код привязки и адрес бота. Код живёт 10 минут и одноразовый; повторный
вызов до истечения отдаёт **тот же** код — админ мог закрыть окно, не дойдя
до телефона. Десять неудачных попыток подряд гасят код досрочно: бот
публичный, и продиктованный вслух код иначе стоял бы открытым все 10 минут
под чужими попытками. Погас — эта же ручка выдаёт новый.

```json
{
  "code": "K7M2XB",
  "bot_username": "lms_kz_bot",
  "deep_link": "https://t.me/lms_kz_bot?start=K7M2XB",
  "expires_at": "2026-08-19T12:40:00Z"
}
```

```json
// 409 bot_not_configured — токен бота не задан в конфигурации сервиса
{ "error": { "code": "bot_not_configured", "message": "Бот не настроен на сервере — задайте токен в конфигурации" } }
```

### POST /telegram/webhook

**Не для фронта.** Сюда стучится сам Telegram. Подлинность проверяется
заголовком `X-Telegram-Bot-Api-Secret-Token`: он задаётся при установке
вебхука и сверяется с конфигурацией. Не совпал — `403`, и в лог не уходит
ничего из тела: там переписка людей.

Понимает одну команду — `/start <код>`. Код верный и живой: `chat_id` чата
записывается в настройки, код гасится, боту уходит подтверждение. Гасится он
условной записью в базе, поэтому два одновременных `/start` с одним кодом
привяжут ровно один чат — второму уходит отказ. Код неверный или просрочен —
боту уходит отказ, а в настройках меняется только счётчик неудачных попыток.

Отвечает `200` **всегда**, что бы ни пришло: Telegram на любой другой ответ
повторяет доставку по нарастающей, и один неудачный разбор превратится
в бесконечный поток. Ошибки разбора уходят в лог без текста сообщения.
Тело больше 64 КБ не разбирается вовсе — ответ на него тот же `200`,
в логе остаётся только факт.

```json
// 200 — тело ответа пустое, Telegram его не читает
{}
```

### POST /admin/settings/telegram/test

Кнопка «Отправить тестовое сообщение». Шлёт в привязанный чат короткий текст
и возвращает `204`. Персональных данных в тестовом сообщении нет — как и
в настоящих: в бот уходят номер заявки и название курса, но не ФИО и не
телефон учителя (`BACKEND_NOTES`, раздел 11).

```json
// 409 telegram_not_connected — бот не привязан
{ "error": { "code": "telegram_not_connected", "message": "Бот не подключён — сначала привяжите чат" } }

// 502 telegram_failed — Telegram не принял сообщение
{ "error": { "code": "telegram_failed", "message": "Telegram не принял сообщение — попробуйте позже" } }
```

Это единственное место, где сбой доставки виден админу как ошибка. Настоящие
уведомления так себя не ведут: заявка сначала пишется в базу и только потом
уходит в бот, и недоступный бот **никогда** не мешает её создать — «Telegram
только доставка, не хранилище» (`BACKEND_NOTES`, раздел 11).

### POST /admin/settings/telegram/unbind

«Отвязать». `204`. Стирает `chat_id`; флаги типов сообщений остаются как были.
После этого уведомления админам не уходят никуда, а заявки продолжают
складываться в админке.

## GET /certificates/{id}/pdf

Сертификат бумагой. Отдаёт **байты PDF** (`application/pdf`), а не ссылку:
файла в хранилище нет, документ собирается в момент запроса из тех же данных,
что и карточка, — ФИО, курс, часы, дата и номер.

Свой документ забирает учитель, любой — админ. Отозванный (`revoked_at`)
не отдаётся никому: отозванная бумага не должна печататься заново. **Заявка
отвечает `404` тем же текстом**, что и отозванный: печатать нечего, а разного
текста на «ещё нет» и «уже нет» посторонний видеть не должен.

Шаблон один и свёрстан в коде (`DESIGN_BRIEF`, 5.25). Из настроек в него
подставляются три картинки — логотип, подпись, печать; каждой может не быть,
и тогда её место остаётся пустым, а документ всё равно выдаётся: отсутствие
печати не повод отказать человеку в сертификате.

На листе печатается **QR на страницу проверки** этого документа
(`DESIGN_BRIEF`, 5.11) и под ним короткий адрес без номера — `domain.kz/verify`.
Адрес берётся из **конфигурации сервиса** (`verify_base_url` и
`platform_verify_urls`), а не из настроек площадки: страница `/verify` живёт
в клиентском приложении, а не в API, и меняется она при смене домена, а не когда
админ правит настройки. Настройка пустая — QR не печатается вовсе, а документ
выдаётся: код, ведущий в никуда, с выданной бумаги уже не исправить.

Адрес — **у площадки самого документа**, а не общий: проверка номера отвечает
только по своей площадке, и QR второй площадки, уводящий на первую, честно
показал бы там «не найдено». Площадку берём из строки сертификата, а не из
запроса, по той же причине, что и картинки бренда: бумагу открывает браузер
прямой ссылкой, `Origin` в такой запрос не приходит. Площадка, у которой своего
адреса в настройке нет, получает общий `verify_base_url` — так собирается ссылка
и у документов, выданных до разделения площадок.

Язык документа — `lang` самого сертификата, а не язык читателя: это снимок,
сделанный в момент выдачи.

```
// 200
Content-Type: application/pdf
Content-Disposition: attachment; filename="KZ-2026-XB7K2M.pdf"
```

Ошибки:

```json
// 401 unauthorized — не залогинен
// 403 forbidden — чужой сертификат, а вы не админ
// 404 not_found — нет такого документа, он отозван или это ещё заявка
```

# Сессия «Платформы 1» — площадка в учебной части

Площадок стало две (`PLATFORMS_BRIEF`, решение владельца 03.09.2026): два домена
с разными брендами на одной админке и одном бэкенде. Аккаунт, база и API общие;
раздельными становятся **доступ, прогресс, попытки, работы и сертификаты**.

**Форма ответов не изменилась почти нигде.** Изменилось, какие строки в них попадают:
эндпоинты ниже отдают только строки своей площадки. Новое поле появилось ровно в двух
местах — обе админские ручки, у которых площадку неоткуда взять (`POST /admin/enrollments`
и `POST /admin/teachers/{id}/retakes`). Фронтам учебных площадок правок не требуется,
кроме одного: **доступ, выданный на одной площадке, курса на другой не открывает**, и
экраны обязаны это переживать как обычный `403`.

## Откуда сервер берёт площадку

По `Origin` запроса — тем же способом, каким отличает админку от кабинета учителя,
и по той же причине: `Origin` единственное, что браузер присылает на каждый запрос
фронта, и он уже проверен CORS. Соответствие «источник → код площадки» задаётся
настройкой `PLATFORM_ORIGINS`.

- Настройка не задана — **предупреждение в лог и первая площадка**, а не отказ сервиса:
  так площадка работала до разделения, и гасить из-за забытой переменной живой API дороже.
- Код площадки вне списка — **сервис не поднимается**. Такую строку отвергнет `CHECK`
  в базе, то есть сервис выглядел бы здоровым и падал на каждой записи учителя.
- Неизвестный источник, отсутствие `Origin` и **админка** — первая площадка. У админки
  площадки нет вовсе: она одна на обе.

Коды площадок — `p1` и `p2`. Слаги нейтральные: бренд переименуют, а колонка в девяти
таблицах и в ключах переживёт переименование без миграции.

## Что теперь значит «своя площадка»

Одинаково для всех перечисленных ручек: строка чужой площадки для запроса **не
существует**. Не «скрыта» и не «запрещена» — её нет, и ответ такой же, как если бы её
не было в базе никогда.

| Ручка | Что фильтруется | Ответ, когда своей строки нет |
|---|---|---|
| `GET /me/courses` | доступы **и заявки** — обе половины ответа | `{ "items": [], "leads": [] }` |
| `GET /lessons/{id}` | действующий доступ своей площадки | `403 forbidden` |
| `POST /lessons/{id}/complete` | доступ; отметка ставится своей площадке | `403 forbidden` |
| `GET /lessons/{id}/playback` | доступ | `403 forbidden` |
| `GET /files/{id}` | доступ к курсу материала | `403 forbidden` |
| `GET /quizzes/{id}`, `/quiz_attempts/*` | доступ, попытки, сертификат | `403 forbidden` / `404 not_found` |
| `GET /tasks/{id}`, `POST /tasks/{id}/submissions` | доступ, история сдач | `403 forbidden` |
| `GET /courses/{id}/completion` | доступ, прогресс, сертификат | `403 forbidden` |
| `POST /courses/{id}/certificate` | доступ, условия, сертификат | `403 forbidden` |
| `GET /me/certificates` | сертификаты своей площадки | `{ "items": [] }` |
| `GET /verify/{number}` | сертификаты своей площадки | `404 not_found` — см. ниже |
| `POST /courses/{id}/lead`, `/reviews` | заявка и отзыв заводятся на своей площадке | — |
| `POST /lessons/{id}/questions` | вопрос заводится на своей площадке | — |

**Прогресс, попытка и сертификат считаются заново на каждой площадке.** Курс, выложенный
на обеих, изучается на каждой отдельно; человек, купивший его дважды, получает две попытки
одного теста и два сертификата. Это принятое владельцем следствие раздельного доступа,
а не дефект.

**Снятая галочка публикации доступа не отбирает** — тот, кто уже учится, доучивается
и получает сертификат.

**Админка платформу не фильтрует** и в этой сессии видит обе площадки целиком: списки
работ на проверку, карточка учителя и отчёт по курсу считаются как прежде. Метка
площадки в списках и фильтр по ней — следующая сессия.

## GET /verify/{number} — чужой номер неотличим от несуществующего

Проверка сертификата отвечает **только по своей площадке**. Номер, выданный на первой,
на второй отвечает ровно как несуществующий: тот же статус, тот же код, тот же текст.
Разный ответ был бы способом узнать, что документ существует, — а страница публичная.

```json
// 404 not_found — номера нет в реестре ЭТОЙ площадки: и когда его нет вовсе,
// и когда он выдан на соседней
{ "error": { "code": "not_found", "message": "Сертификат не найден" } }
```

Номер при этом **уникален на всю базу**: площадки делят одну нумерацию, иначе проверка
по номеру перестала бы быть однозначной. Двух документов с одним номером не бывает.

`GET /certificates/{id}/pdf` площадку **не проверяет** и остаётся как был: ссылку
открывает браузер напрямую, `Origin` в такой запрос не приходит, и фильтр отказывал бы
в печати сертификата второй площадки. Права там прежние — свой документ или админ.

## POST /admin/enrollments — площадка обязательна

Единственная ручка выдачи доступа. Админка одна на обе площадки, её `Origin` площадки
не несёт — **угадать её здесь неоткуда, поэтому она приходит телом и обязательна**.
Забытое поле — отказ, а не молчаливая первая площадка: доступ, выданный не на ту
площадку, человек увидит не на том сайте.

Доступ уникален тройкой «учитель + курс + площадка»: тот же курс на второй площадке —
это второй доступ, со своим прогрессом и своим сертификатом. Закрывается заявка **своей
площадки**, уведомление в колокольчик уходит с площадкой созданного доступа.

```json
// запрос
{ "user_id": 1, "course_id": 1, "platform": "p1", "paid": true, "note": "Kaspi, перевод 16.08" }

// 200
{
  "id": 7,
  "user_id": 1,
  "course_id": 1,
  "platform": "p1",
  "granted_at": "2026-08-16T09:30:00Z",
  "paid": true,
  "note": "Kaspi, перевод 16.08"
}
```

Ошибки:

```json
// 404 not_found — нет учителя; нет курса, черновик или скрытый

// 409 already_enrolled — доступ на ЭТОЙ площадке уже действует. На соседней
// площадке тот же курс тем же ответом не закрывается
{ "error": { "code": "already_enrolled", "message": "Доступ к курсу уже открыт" } }

// 422 — площадка не названа или названа неизвестным кодом
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "platform", "message": "Field required" } ] }
  }
}
```

## POST /admin/teachers/{id}/retakes — площадка обязательна

По той же причине и с той же ценой ошибки. «Разрешить пересдачу» снимает зачёт
с попытки, а у человека с курсом на обеих площадках зачётных попыток две — по одной
на каждой. Снять зачёт не с той — это отнятая у человека попытка, поэтому площадка
называется явно.

```json
// запрос
{ "quiz_id": 5, "platform": "p1", "reason": "Пропал интернет во время попытки" }
```

Ответ прежний — карточка учителя целиком. Ошибки прежние, плюс `422`, когда площадка
не названа или названа неизвестным кодом.

## Чего в этой сессии ещё нет

Чтобы следующая фронтовая сессия не искала это в ответах:

- **Каталог, карточка курса, отзывы и вопросы площадку пока не фильтруют** — это
  следующая бэкенд-сессия вместе с публикацией и ценой на площадку (`course_platform`).
  `course.price` продолжает читаться из прежней колонки.
- **Колокольчик** отдаёт уведомления обеих площадок: колонка у них уже проставлена,
  чтение по ней — следующая сессия.
- **Метки площадки в админских списках** (заявки, отзывы, вопросы, работы) и фильтр
  по площадке — следующая сессия.
- **`GET /settings` собирается из таблицы `setting`, как раньше**; бренд в код и
  `GET /branding/{slot}` по площадке — следующая сессия.

**Одно предупреждение вперёд.** Пока каталог площадку не фильтрует, курс, не выложенный
на этой площадке, всё ещё «существует» для неё, и без доступа его двери отвечают
`403 forbidden`. Когда следующая сессия включит публикацию по площадке, часть этих
отказов станет `404 not_found` — курса на этой площадке не будет вовсе. Экранам стоит
переживать оба ответа одинаково: «этого курса у вас нет».

# Сессия «Платформы 2» — каталог, цены и бренд

Вторая половина перехода на две площадки (`PLATFORMS_BRIEF`). Сессия 1 завела
колонки и ключи и разделила учебную часть; здесь площадка доходит до **каталога,
цены, отзывов, вопросов, колокольчика и админских списков**, а бренд уезжает
из базы в код.

**Это первая сессия перехода, которая формы ответов меняет и убирает,** а не только
добавляет. Полный список — сразу ниже, он сверен со схемой OpenAPI: ни одного
изменения мимо этого файла нет.

## Что изменилось в формах — список целиком

| Схема | Было | Стало |
|---|---|---|
| `AdminCourseOut`, `AdminCourseCardOut` | `price: int \| null` | `platforms: [{ platform, price }]` |
| `AdminCoursePatchIn` | `price: int \| null` | `platforms: [{ platform, price }] \| null` |
| `AdminSettingsOut` | `platform_name`, `org_name`, `logo`, `contacts`, `certificate_images`, `telegram` | `platforms: [{ platform, platform_name, org_name }]`, `telegram` |
| `AdminSettingsPatchIn` | `platform_name`, `org_name`, `contacts`, `logo`, `certificate_images`, `telegram` | `telegram` |
| `AdminLeadOut`, `AdminSubmissionOut`, `AdminSubmissionCardOut`, `AdminQuestionOut`, `AdminReviewOut` | — | **добавлено** `platform` |
| `OverviewLeadOut`, `OverviewSubmissionOut`, `OverviewQuestionOut` | — | **добавлено** `platform` |
| `ReportParticipantOut` | — | **добавлено** `platform`; строка теперь = доступ, а не человек |
| убраны совсем | `SettingsImageIn`, `SettingsImageOut`, `AdminCertificateImagesIn`, `AdminCertificateImagesOut`, `SettingsContactsIn` | — |

Новые параметры запроса: `?platform=` у `GET /admin/leads`, `/admin/submissions`,
`/admin/questions`, `/admin/reviews`, `/admin/overview`, `/admin/reports/{course_id}`
и `GET /branding/{slot}`.

**`GET /settings` форму не изменил ни на поле** — поменялся только источник.
Не изменились и все учительские ручки: каталог, страница курса, «Мои курсы»,
отзывы, вопросы, колокольчик отдают то же, что отдавали. Изменилось, **какие
строки** в это попадают.

## Что теперь значит «курс есть на этой площадке»

Правило одно, и оно двойное:

> Курс существует для площадки, если он на ней **выложен** — или если у человека
> есть **действующий доступ** на ней.

Выложен — значит есть строка `course_platform (course_id, platform, price)`; её
создаёт и удаляет галочка в редакторе курса. Вторая половина правила — прямое
следствие решения 12 договорённости: **снятая галочка не отбирает доступ.** Курс
уходит из каталога площадки, а тот, кто уже учится, доучивается и получает
сертификат. Иначе снятие галочки становилось бы необратимым действием над чужой
учёбой.

Отсюда — где что отвечает:

| Ручка | Курс не выложен, доступа нет | Курс не выложен, доступ есть |
|---|---|---|
| `GET /courses` | курса нет в списке | курса нет в списке |
| `GET /courses/{id}` | `404 not_found` | `200`, цена `null` |
| `GET /courses/{id}/reviews` | `404 not_found` | `404` — лента публичная, поблажка по доступу к ней не относится |
| `GET /courses/{id}/program` | `404 not_found` | `200` |
| `POST /courses/{id}/lead` | `404 not_found` | заявку подавать незачем — доступ уже есть |
| `GET /lessons/{id}` и остальные двери учебной части | `403 forbidden` | `200` |
| `POST /courses/{id}/certificate` | `403 forbidden` | `200` |

**Двери учебной части остались на `403`.** `CONTRACT` сессии «Платформы 1»
предполагал, что часть этих отказов станет `404`, — не стала: запирать урок
публикацией значило бы отобрать учёбу у того, кто её уже оплатил. `404` появился
только там, где спрашивают каталог: страница курса, лента отзывов и заявка.

## Цена — свойство пары «курс и площадка»

`course.price` больше нет: колонку убрала ревизия `e6a41d0c7b58`. Цена везде
приезжает из `course_platform`.

- `GET /courses`, `GET /courses/{id}`, `GET /me/courses` — цена **своей** площадки.
  Курс сняли с площадки, а человек на нём учится — `price: null`, «Цена по запросу».
- `POST /courses/{id}/lead` — снимок цены берётся с площадки, **с которой пришла
  заявка**. `price_snapshot` в заявке потом не меняется, как и раньше.
- `GET /admin/leads` — цена рядом с заявкой это цена **её** каталога
  (`course.price` в строке заявки считается по `lead.platform`).

```json
// GET /courses/1, Origin первой площадки — тот же курс, своя цена
{ "id": 1, "title": "Критериальное оценивание в начальной школе", "price": 45000, "…": "…" }

// GET /courses/1, Origin второй
{ "id": 1, "title": "Критериальное оценивание в начальной школе", "price": 60000, "…": "…" }
```

## Отзывы, вопросы и колокольчик — каждый в своём каталоге

Формы не изменились; изменился состав.

- **Отзывы.** `GET /courses/{id}/reviews`, `total`, `breakdown` и рейтинг курса —
  по своей площадке. Прошедший курс дважды оставляет два отзыва, по одному
  в каждом каталоге, и один в другом не виден (`PLATFORMS_BRIEF`, решения 3 и 15).
  `rating` и `reviews_count` в каталоге и на карточке курса тоже считаются по своей.
- **Вопросы.** `GET /lessons/{id}/questions` показывает тред своей площадки —
  и в `items`, и в `total`. Ответ ложится на площадку **своего вопроса**, а не
  запроса: админ отвечает из общей очереди, и тред остаётся целым там, где вопрос
  задан.
- **Колокольчик.** `GET /notifications` — уведомления своей площадки, вместе
  с `total` и `unread_count`. `POST /notifications/read` помечает только свои:
  id уведомления соседней площадки неотличим от чужого — `204`, ничего
  не помечено. «Прочитать все» на одной площадке не гасит непрочитанное
  на второй.

## Редактор курса: публикация и цены

**Изменено в сессии «Платформы 2».** У курса больше нет поля `price` — ни на чтение,
ни на запись. Вместо него `platforms`: галочка публикации и цена это один элемент
списка.

```json
// GET /admin/courses/{id} и строка GET /admin/courses — только выложенные площадки,
// порядком p1, p2
"platforms": [
  { "platform": "p1", "price": 45000 },
  { "platform": "p2", "price": 60000 }
]

// курс, не выложенный нигде: только что созданный, новая языковая версия, дубликат
"platforms": []
```

`PATCH /admin/courses/{id}`:

- поля `platforms` в запросе нет — набор площадок не трогаем;
- поле есть — присланный список **заменяет набор целиком**: чего в нём нет,
  то снято. Список всегда полный;
- `price` внутри элемента **обязателен** и может быть `null` («Цена по запросу»):
  так запрос и ответ совпадают один в один, и забытое поле не стирает цену молча;
- **снятие галочки не отказывается никогда**, даже если по курсу учатся. Это
  не «правка курса, где уже учатся»: содержимое не трогается, учёба продолжается,
  курс лишь уходит из каталога.

```json
// 422 — одна площадка в списке дважды
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": { "fields": [ { "field": "platforms", "message": "Площадка в списке дважды: p1" } ] }
  }
}
```

Отрицательная цена отвечает как прежде: `{ "field": "price", "message": "Цена не может быть отрицательной" }`.

## Метка площадки и фильтр в админке

Админка одна на обе площадки и **по умолчанию показывает обе**.

**Метка** — поле `platform` (`"p1"` / `"p2"`) в строке списка, рядом с `id`.
Появилось в `GET /admin/leads` и `PATCH /admin/leads/{id}`, `GET /admin/submissions`,
`GET /admin/submissions/{id}` и `POST /admin/submissions/{id}/review`,
`GET /admin/questions`, `GET /admin/reviews` и `POST /admin/reviews/{id}/reply`,
а также в трёх списках `GET /admin/overview`. Ручка, отдающая карточку той же
строки, отдаёт и метку: после сохранения она не должна пропадать с экрана.

Метка — **код, а не имя**. Человеческое имя площадки админка берёт из справочника
`GET /admin/settings`.

**Фильтр** — `?platform=p1`, одно значение, не список. Параметра нет — обе площадки.
Фильтр сочетается с остальными (`status`, `course_id`, `rating`, `answered`, `q`)
и отсекает не только страницу, но и `total`.

```json
// 422 — площадка вне списка
{ "error": { "code": "validation_error", "message": "Неизвестная площадка: px" } }
```

## Сводка и отчёт — общие числа плюс фильтр

Решение 9 договорённости: вторых колонок у показателей не появляется. У обеих ручек
один фильтр `?platform=`, и он действует на всё сразу.

- `GET /admin/overview` — на три счётчика, на три списка и на `totals`.
  `totals.teachers` — **исключение и считается по обеим всегда**: аккаунт один
  на обе площадки (решение 11), колонки площадки у человека нет, и «учитель
  площадки» был бы новым понятием, которого в договорённости нет.
- `GET /admin/reports/{course_id}` — на сводку, воронку и таблицу участников.

**Строка таблицы участников — это доступ, а не человек.** У человека с доступом
на обеих площадках строк две, у каждой своя `platform`, свой прогресс, свой
итоговый тест и свой сертификат; `granted` и `total` считают доступы. Так закрыт
дефект сессии «Платформы 1»: раньше отчёт соединял человека с доступом без учёта
площадки, и проценты такого человека складывались по обеим.

```json
// GET /admin/reports/1 — один человек, два доступа
"participants": { "items": [
  { "user_id": 2, "platform": "p1", "last_name": "…", "progress_percent": 75,
    "final_quiz": { "state": "passed", "score": 100 }, "certificate": "issued" },
  { "user_id": 2, "platform": "p2", "last_name": "…", "progress_percent": 25,
```

# Сессия «Платформы 3» — площадка в карточке учителя

Админская сессия перехода на две площадки. В бэкенде она трогает **одну ручку** —
карточку учителя, и по одной причине: без площадки в строке админ выбирает её
вслепую, а кнопка «Разрешить пересдачу» может гореть там, где сервер ответит `409`.
Это открытый вопрос 2 сессии «Платформы 1», не закрытый сессией 2.

Всё остальное этой сессии — фронт админки, и в контракте ему места нет.

## Что изменилось в формах — список целиком

Четыре схемы, по одному обязательному полю. Сверено со схемой OpenAPI
до и после: ни путей, ни других схем сессия не тронула.

| Схема | Было | Стало |
|---|---|---|
| `AdminTeacherEnrollmentOut` | — | **добавлено** `platform` |
| `AdminTeacherQuizOut` | — | **добавлено** `platform`; строка теперь = **тест на площадке**, а не тест |
| `AdminTeacherSubmissionOut` | — | **добавлено** `platform` |
| `AdminTeacherCertificateOut` | — | **добавлено** `platform` |

Ни одного нового пути, ни одного нового параметра запроса. `POST
/admin/teachers/{id}/retakes` не менялся вовсе: площадку он требовал телом
с сессии «Платформы 1».

## GET /admin/teachers/{id} — строка вкладки это площадка

Аккаунт один на обе площадки (`PLATFORMS_BRIEF`, решение 11), а доступ, прогресс,
попытка, работа и сертификат — раздельные (решение 2). Значит у одного человека
по одному курсу может быть **две независимые учёбы**, и карточка обязана их
различать: иначе две одинаковые строки читаются как дубль и баг.

- **«Курсы»** — по строке на доступ, как и было; теперь у строки есть `platform`.
  `lessons_done`, `lessons_total` и `progress_percent` считаются **по паре «курс
  и площадка»**: урок, пройденный на первой, процент на второй не двигает.
  До этой сессии прогресс складывался по обеим и у человека с двумя доступами
  показывал одно удвоенное число в двух строках.
- **«Тесты»** — по строке на **тест и площадку**, внутри только попытки этой
  площадки. У одного теста строк может быть две, с разным итогом.
- **«Работы»** — `platform` у сдачи: одно задание, сданное на обеих, это две
  разные работы с разной судьбой проверки.
- **«Документы»** — `platform` у сертификата: по одному курсу их может быть два,
  по одному на площадку, с разными номерами.

**`can_allow_retake` и `retake_blocker` считаются на площадку строки** — по её
попыткам и по сертификату **этой** площадки. То, что показано в строке, совпадает
с тем, что ответит сервер, если послать пересдачу с этой же `platform`. Кнопка
и сервер больше не расходятся ни в одну сторону.

```json
// человек купил общий курс дважды: два доступа, две строки теста
"courses": [
  { "enrollment_id": 5, "course": { "id": 1, "lang": "ru", "title": "…" },
    "platform": "p1", "lessons_done": 12, "lessons_total": 18, "progress_percent": 60, "…": "…" },
  { "enrollment_id": 9, "course": { "id": 1, "lang": "ru", "title": "…" },
    "platform": "p2", "lessons_done": 2, "lessons_total": 18, "progress_percent": 10, "…": "…" }
],

// сертификат по курсу выдан на p1 — там пересдача закрыта, на p2 открыта
"quizzes": [
  { "quiz_id": 1, "title": "Тест модуля 1", "course_id": 1, "course_title": "…",
    "platform": "p1", "retakable": false, "pass_score": 70,
    "can_allow_retake": false, "retake_blocker": "certificate_issued",
    "attempts": [ { "id": 4, "score": 55, "passed": false, "is_counted": true, "…": "…" } ] },
  { "quiz_id": 1, "title": "Тест модуля 1", "course_id": 1, "course_title": "…",
    "platform": "p2", "retakable": false, "pass_score": 70,
    "can_allow_retake": true, "retake_blocker": null,
    "attempts": [ { "id": 11, "score": 40, "passed": false, "is_counted": true, "…": "…" } ] }
],

"submissions": [ { "id": 4, "task_id": 1, "task_title": "…", "course_id": 1,
                   "platform": "p1", "status": "rework", "…": "…" } ],

"certificates": [ { "id": 7, "number": "KZ-2026-XB7K2M", "course_id": 3,
                    "platform": "p1", "course_title": "…", "hours": 36, "…": "…" } ]
```

**Метка — код, а не имя**, как и в остальных админских списках: человеческое имя
площадки экран берёт из справочника `platforms` в `GET /admin/settings`.

`PATCH /admin/teachers/{id}` и `POST /admin/teachers/{id}/retakes` отдают ту же
карточку — значит и они отдают `platform` во всех четырёх вкладках.

## Чего в этой сессии нет

- **`GET /admin/teachers` (список) площадку не знает и не фильтрует.** Аккаунт
  один на обе площадки, «учитель площадки» — понятие, которого в договорённости
  нет (то же исключение, что у `totals.teachers` в сводке). `courses_count`
  в строке списка считает **доступы**: у человека с общим курсом на обеих их два.
- **Числа сессий «Платформы 1» и «Платформы 2» не пересматривались** — эта сессия
  ничего, кроме карточки, в бэкенде не трогала.


# Сессия «Платформы 6» — адрес проверки у каждой площадки свой

Фронтовая сессия вёрстки второй площадки. В бэкенде она трогает **одну
настройку** и одно место, которое её читает: без этого QR на сертификате второй
площадки уводил бы на первую, и там честно писалось бы «не найдено». Ошибка
такого рода видна не сразу — код уже напечатан на бумаге.

**Форм и путей сессия не меняет.** Схема OpenAPI сверена до и после: ни одной
новой схемы, ни одного нового поля, ни одного изменённого ответа. Меняется
только содержимое QR-кода внутри PDF — то есть данные, а не контракт.

## Что изменилось

| Настройка | Было | Стало |
|---|---|---|
| `VERIFY_BASE_URL` | адрес страницы проверки, один на обе площадки | он же, но теперь это **адрес по умолчанию**: его получает площадка, у которой нет своего |
| `PLATFORM_VERIFY_URLS` | — | **добавлена**: «код площадки → адрес её страницы проверки», объектом JSON |

`GET /certificates/{id}/pdf` собирает ссылку для QR по площадке **самого
документа** (`certificate.platform`), а не по площадке запроса и не из общей
настройки. Причина та же, по которой оттуда же берутся картинки бренда: бумагу
открывает браузер прямой ссылкой, `Origin` в такой запрос не приходит,
и площадки у него нет вовсе.

Проверки при старте — как у `PLATFORM_ORIGINS`, и цена ошибки та же:

- код площадки вне `p1`/`p2` **роняет старт**: адрес не достался бы никому,
  и QR печатался бы с чужого домена;
- площадка, которую сервис знает по `PLATFORM_ORIGINS`, но без своего адреса
  проверки, — **предупреждение в лог**, сервис поднимается: пока площадка одна,
  общего адреса ей хватает, и гасить из-за этого живой API дороже.

## Чего в этой сессии нет

- **Бренд второй площадки остаётся плейсхолдером.** Имя, организация, контакты
  и четыре картинки `p2` — решение владельца: настоящих значений он пока
  не давал. `BRANDS` и `app/assets/brands/p2/` не тронуты.
- **Числа предыдущих сессий не пересматривались** — эта сессия ничего, кроме
  адреса проверки, в бэкенде не трогала.

# Сессия «Сертификаты 1» — документ выписывает админ

Сертификат перестал выписываться сам. Учитель **просит** документ, а выдаёт его
**админ** — руками, вводя регистрационный номер академии. И у каждого учителя
появился **ИИН**: без него сертификат не выдать (`CERTIFICATES_BRIEF.md`,
решение владельца 04.09.2026).

## Строка `certificate` теперь бывает в трёх состояниях

Отдельной таблицы заявок нет — это та же строка до выдачи:

| состояние | `requested_at` | `number` | `issued_at` | `revoked_at` |
|---|---|---|---|---|
| `requested` — заявка | есть | `null` | `null` | `null` |
| `issued` — документ | есть | есть | есть | `null` |
| `revoked` — отозван | есть | как было | как было | есть |

Существующий частичный уникальный индекс `uq_certificate_active
(user_id, course_id, platform) WHERE revoked_at IS NULL` заодно не даёт
попросить сертификат дважды. Новая проверка базы `ck_certificate_issued`
держит инвариант `(number IS NULL) = (issued_at IS NULL)`: номер и дата
выдачи появляются одним движением — выдачей.

## Что изменилось в формах — список целиком

| Ручка | Что изменилось |
|---|---|
| `POST /courses/{id}/certificate` | больше не выдаёт документ, а **создаёт заявку**; ответ — состояние строки, а не документ |
| `GET /courses/{id}/completion` | `can_issue` → **`can_request`**; `certificate` — состояние строки, а не «выданный документ» |
| `GET /me/certificates` | добавлен `registration_number`; заявки сюда не попадают |
| `GET /verify/{number}` | добавлен `registration_number` |
| `GET /me`, `PATCH /me` | добавлен `iin`; `onboarding_done` у учителя теперь требует и его |
| `GET /admin/overview` | добавлен `certificates_count` — заявки, ждущие выдачи |
| `GET /admin/teachers/{id}` | добавлен `iin`; во вкладке «Сертификаты» — `status`, `registration_number`, `requested_at`, а `number` и `issued_at` стали необязательными |
| `GET/PATCH /admin/settings` | у `telegram` третий флаг `notify_certificates` |
| **новые** | `GET /admin/certificates`, `GET /admin/certificates/{id}`, `POST /admin/certificates/{id}/issue`, `PATCH /admin/certificates/{id}`, `POST /admin/certificates/{id}/revoke` |

Схемы `CertificateOut` и `CertificateBriefOut` удалены: первая была ответом
мгновенной выдачи, второй — «уже выданный документ в чек-листе».

## ИИН

12 цифр **строкой**: ведущий ноль значащий, число его съест. `000000000000` —
метка «не заполнен» у всех, кто зарегистрировался до 04.09.2026; настоящего
такого номера не бывает, и вписать её себе руками нельзя.

- **Уникален**, кроме заглушки: частичный индекс `uq_user_iin ... WHERE iin <>
  '000000000000'`.
- **Контрольная цифра не проверяется** — требуем ровно 12 цифр. Формула поймала
  бы опечатку, но ошибка в нашей реализации заперла бы живого человека снаружи
  собственного аккаунта: цена ошибки несимметрична.
- **Обязателен учителю, не нужен админу.** `onboarding_done` у админа от ИИН
  не зависит: он не учится и сертификатов не получает.
- **Персональные данные.** Не попадает в логи, в тексты ошибок, в аналитику,
  в уведомления и в карточку Telegram. Наружу уходит только админу — в списке
  сертификатов и в карточке учителя — и самому человеку в `GET /me`.
- **Печатается на бумаге**, потому что нужен академии в реестре, и **не
  показывается на `/verify`**: ту страницу открывает посторонний.

## PATCH /me — ИИН

```json
{"iin": "909900000042"}
```

`null` здесь — «не трогать», а не «стереть»: снять ИИН нельзя, как и язык.

Не 12 цифр (а также буквы, пробелы внутри и сама заглушка) — 422:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "details": {"fields": [{"field": "iin", "message": "ИИН — 12 цифр"}]}
  }
}
```

Номер уже стоит в чужом аккаунте — 409:

```json
{
  "error": {
    "code": "iin_taken",
    "message": "Этот ИИН уже указан в другом аккаунте"
  }
}
```

**`details` пустые нарочно**, и этим отказ отличается от `phone_taken`, который
отдаёт `user_id`: там админ чинит доступ конкретному человеку, а сюда упирается
кто угодно, и назвать аккаунт значит отдать его тому, кто перебирает чужие
номера. Свой же номер занятым не считается — повторное сохранение профиля
проходит.

## GET /courses/{id}/completion

Условий у курса нет — чек-лист пуст, а просить можно сразу:

```json
{"conditions": [], "can_request": true, "blocker": null, "certificate": null}
```

Заявка подана — кнопка гаснет, и человек видит, что ждёт:

```json
{
  "conditions": [],
  "can_request": false,
  "blocker": null,
  "certificate": {
    "id": 1,
    "status": "requested",
    "number": null,
    "requested_at": "2026-09-04T14:31:44.435547Z",
    "issued_at": null
  }
}
```

Админ выдал:

```json
{
  "conditions": [],
  "can_request": false,
  "blocker": null,
  "certificate": {
    "id": 1,
    "status": "issued",
    "number": "KZ-2026-42BTXT",
    "requested_at": "2026-09-04T14:31:44.435547Z",
    "issued_at": "2026-09-04T14:31:44.511998Z"
  }
}
```

`can_request` называется так, а не `can_issue`: кнопка на экране — «Запросить
сертификат», и имя поля обязано говорить, что она делает.

## POST /courses/{id}/certificate

Тела запроса нет. Ответ — состояние строки, той же формы, что в `completion`:

```json
{
  "id": 1,
  "status": "requested",
  "number": null,
  "requested_at": "2026-09-04T14:31:44.435547Z",
  "issued_at": null
}
```

**Повтор идемпотентен**: 200 и та же строка — заявка или уже выданный документ.
Второго сообщения в Telegram повтор не шлёт: заявка уже стоит в очереди админа.

Отказы, по порядку проверок: `forbidden` (доступ к курсу не открыт),
`conditions_not_met` (чек-лист уходит в `details` целиком),
`attempt_in_progress`, `profile_incomplete` (не заполнены фамилия и имя) и —
новый —

```json
{
  "error": {
    "code": "iin_required",
    "message": "Заполните ИИН — без него сертификат не выдать"
  }
}
```

Самого номера в отказе нет и быть не может.

**В режиме предпросмотра** заявка не создаётся: ответ той же формы с `id: 0`,
ни строки в базе, ни сообщения в бот (`BACKEND_NOTES`, раздел 12).

## Заявка в Telegram

Уходит в тот же чат, что заявки на курс и работы на проверку, с меткой площадки
первой строкой. Флаг `notify_certificates` — третий рядом с двумя прежними,
по умолчанию включён.

```
Заявка на сертификат
Площадка: Институт науки и образования будущего
Курс: Критериальное оценивание в начальной школе
[Открыть в админке] → {ADMIN_BASE_URL}/certificates/1
```

**Ни ФИО, ни ИИН в карточке нет**: подробности админ откроет по кнопке —
сообщение уходит в мессенджер, а не за дверь со входом.

## GET /admin/certificates

`?status=requested|issued|revoked` — три вкладки экрана; параметра нет — все три.
`?platform=p1` — общий фильтр админки. `?q=` ищет по ФИО (и живому, и снимку
`holder_name`), **ИИН**, нашему номеру и регистрационному; телефона в поиске нет,
его на этом экране не показывают. Страницы — общего вида.

```json
{
  "items": [
    {
      "id": 1,
      "status": "requested",
      "platform": "p1",
      "number": null,
      "registration_number": "",
      "holder_name": "Нурланова Айгуль Серикқызы",
      "course_id": 1,
      "course_title": "Критериальное оценивание в начальной школе",
      "hours": 72,
      "lang": "ru",
      "requested_at": "2026-09-04T14:31:44.435547Z",
      "issued_at": null,
      "revoked_at": null,
      "teacher": {
        "id": 1,
        "last_name": "Нурланова",
        "first_name": "Айгуль",
        "middle_name": "Серикқызы",
        "iin": "909900000042"
      }
    }
  ],
  "total": 1,
  "page": 1,
  "per_page": 20
}
```

Пустой список — `{"items": [], "total": 0, "page": 1, "per_page": 20}`.

Всё, что описывает документ, — снимки из его собственной строки: курс
переименуют или сократят часы, выданная бумага от этого не меняется. Учитель,
наоборот, живой: ФИО и ИИН админ сверяет с профилем **перед** выдачей, а в снимке
ИИН нет и не будет. Порядок — по `requested_at`, свежие сверху: у заявки даты
выдачи нет, а первое, зачем админ открывает экран, — очередь.

## Карточка и три действия

`GET /admin/certificates/{id}`, `POST .../issue`, `PATCH .../{id}` и
`POST .../revoke` отвечают **одной формой** — карточкой и предупреждением, чтобы
экран перерисовывался одним и тем же куском кода:

```json
{"certificate": { ... то же, что строка списка ... }, "warning": null}
```

Отзыв — `POST .../revoke`, а не `DELETE`: он парный «Выдать», и ответом уходит
карточка целиком, которой у 204 быть не может.

### POST /admin/certificates/{id}/issue

```json
{"registration_number": "АО-2026/0417"}
```

Номер обязателен: выдача без него — документ, которого нет в реестре академии.
В эту секунду появляются наш номер, дата выдачи и PDF; учителю уходит
уведомление `certificate_issued`, а у его доступа проставляется `completed_at` —
«курс пройден» и «сертификат выдан» теперь одно событие, и вкладка «Пройденные»
на `/my` держится на нём.

```json
{
  "certificate": {
    "id": 1,
    "status": "issued",
    "platform": "p1",
    "number": "KZ-2026-42BTXT",
    "registration_number": "АО-2026/0417",
    "holder_name": "Нурланова Айгуль Серикқызы",
    "course_id": 1,
    "course_title": "Критериальное оценивание в начальной школе",
    "hours": 72,
    "lang": "ru",
    "requested_at": "2026-09-04T14:31:44.435547Z",
    "issued_at": "2026-09-04T14:31:44.511998Z",
    "revoked_at": null,
    "teacher": {"id": 1, "last_name": "Нурланова", "first_name": "Айгуль",
                "middle_name": "Серикқызы", "iin": "909900000042"}
  },
  "warning": null
}
```

Отказы: `not_found`; `conflict` — «Сертификат отозван — выдать его снова
нельзя»; `certificate_issued` — «Сертификат уже выдан — правьте его через
«Сохранить»»; `validation_error` с полем `registration_number`;
`iin_required` — «У учителя не заполнен ИИН — сертификат выдать нельзя».
ИИН спрашивается второй раз после заявки нарочно: между заявкой и выдачей
проходит время, а без номера человека не внести в реестр.

### Повтор регистрационного номера — предупреждение, а не отказ

Документ **сохранён**, и вместе с ним приходит `warning`:

```json
{
  "code": "registration_number_taken",
  "message": "Такой номер уже есть у сертификата №KZ-2026-M2HN5R",
  "certificate_id": 1,
  "number": "KZ-2026-M2HN5R"
}
```

Правил чужой нумерации мы не знаем, а запрет остановил бы админа посреди работы
(`CERTIFICATES_BRIEF`, 2). Предупреждение приходит только в ответ на запись:
при открытии карточки его нет — оно отвечает на то, что админ только что ввёл,
а не висит у документа постоянной меткой.

### PATCH /admin/certificates/{id}

Правятся снимки на бумаге и то, что админ вписал руками:
`registration_number`, `holder_name`, `course_title`, `hours`, `lang`,
`issued_at`. Всё остальное — `number`, `user_id`, `course_id`, `platform` —
отбивает `extra: forbid`: смена любого означает другой документ, а не правку
этого.

`issued_at` у невыданной строки — 409 `certificate_not_issued`, «Сертификат ещё
не выдан — дату выдачи ставит выдача». Присланный `issued_at: null` — отказ по
полю: стёртая дата отменила бы выдачу в обход отзыва, а наш номер остался бы за
строкой. Пустой `registration_number` допускается — так админ стирает ошибочный.

### POST /admin/certificates/{id}/revoke

Работает и над выданным документом, и над **заявкой**: снять ошибочную заявку
больше нечем, а отозванная строка освобождает `uq_certificate_active` — и
человек может попросить сертификат снова. Повторный отзыв ничего не меняет:
время остаётся временем первого. Уведомления учителю нет — типа
`certificate_revoked` в `domain/notifications.py` не существует.

Оба номера: комиссии номер академии полезнее нашего. **ИИН здесь нет и не
будет** — страницу открывает посторонний человек.

У документов до 04.09.2026 `registration_number` пустой, пока админ не проставит
его на новой странице. Заявка сюда не попадает по построению: номера у неё нет.

## Бумага

На листе рядом с датой и нашим номером встали ещё две подписи: **ИИН** слева
и **регистрационный номер** справа. Пустое значение свою половину строки не
печатает вовсе — у документов до 04.09.2026 лист выходит ровно как раньше.
Заглушка ИИН на бумагу не идёт: она читалась бы как настоящий номер из нулей.

ИИН берётся из живой таблицы `user` — **единственное поле листа не из снимка**.
Колонки `iin` у сертификата нет и не заводится: номер у человека один на всю
жизнь, а вторая копия самых чувствительных персональных данных — это две утечки
вместо одной.

`GET /certificates/{id}/pdf` для заявки отвечает **404 тем же текстом**, что и
для отозванного: печатать нечего, а разного текста на «ещё нет» и «уже нет»
посторонний видеть не должен.

## Заявка закрывает тесты так же, как выданный документ

Действующая строка сертификата — и заявка тоже — закрывает старт теста и
пересдачу. Причина: админ выпишет документ по тому чек-листу, который был
проверен в момент заявки, и поехавшие после неё результаты дали бы бумагу
человеку, который условиям больше не отвечает. Код отказа прежний,
`certificate_issued`, а текст свой:

```json
{
  "error": {
    "code": "certificate_issued",
    "message": "Заявка на сертификат отправлена — результаты теста изменить нельзя"
  }
}
```

Ошибочную заявку снимает отзыв — и тесты снова открываются.

## Чего в этой сессии нет

- **Уведомления об отзыве** — типа `certificate_revoked` не существует, и
  заводить текст, которого не просили, сюда не входит.
- **Списка под счётчиком `certificates_count`** на дашборде: там три списка,
  четвёртый никто не просил.
- **Пометки «ИИН не сходится»** в админке: её не просили, а лишний красный
  значок рядом с чужими персональными данными живёт своей жизнью.
- **Проверки регистрационного номера на уникальность** — по решению владельца
  это предупреждение, а не запрет.
- **Экранов.** Страница «Сертификаты» в админке — сессия 2, ИИН в онбординге и
  «Запросить сертификат» на обеих площадках — сессия 3.
